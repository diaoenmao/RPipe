# 一、目的与适用范围
研究计划用于说明要解决什么问题、现有证据支持到哪里、准备怎样验证，以及什么结果会改变当前判断。AI 研究统一考虑六个方面：**文献调研、数据、模型、算法、指标、实验设计**，并将它们连接到明确的研究问题与假设。
本规范适用于文献综述、理论分析、方法创新、复现、Benchmark 和系统研究，也可按研究对象迁移到其他科学领域。模型可以是神经网络、统计模型、数学模型或机制模型，算法可以是训练、推理、求解或分析过程。
制定日期：2026年10月11日。更新日期：2026年10月16日。状态：建议采用，具体课题的路线、预算、负责人和期限由该课题另行确认。
本规范提供研究思路，六个方面按课题需要展开，可以合并或简写。理论研究可用证明、反例和复杂度分析回应验证安排，纯文献调研可止于证据比较和缺口分析。来源真实、实际工作范围清楚、结论有据可查是基本原则。
AI 辅助研究时，可将这些思路展开为检查提示，帮助发现遗漏、记录差异和安排下一步。具体步骤、复现精度和记录粒度按研究问题判断，不把每项检查都设为推进条件。

# 二、从灵感形成研究计划
基本流程为：**灵感 → 文献调研 → 研究问题与假设 → 联合规划数据、模型、算法、指标与实验 → 执行与分析 → 结论及新的灵感**。初步问题帮助检索，正式问题在调研后进一步明确，文献和实验结果也可以触发新的灵感。[6][7]
## （一）灵感
记录想法、异常观察、实践困难或对既有解释的疑问，注明来源和触发条件。用一句话说明“可能存在什么问题或机会”，再提出用于检索的初步问题。此时的新颖性和可行性保留为待验证。
## （二）文献调研
围绕初步问题核查已有工作、替代解释、强基线和证据缺口，同时提取数据、模型、算法、指标与实验条件。调研后说明灵感已被解决、值得继续、需要调整还是暂时搁置，具体方法见第三章。
## （三）研究问题与假设
先写清研究对象、使用条件、现有不足、预期改进和范围。将问题写成可以回答的句子，例如“在固定模型和测试分布下，后处理方法能否改善概率校准，同时满足准确率与计算成本约束？”
假设应说明可能的机制和能够反驳它的观察。发现性调研可以先列研究问题，在形成证据后再提出假设。与最接近工作的差异须给出依据，尚未核验的新颖性写为“待验证”。
假设检验应明确可反驳的预测及不确定性，探索性研究可以先提出问题再形成假设，后续独立验证时区分发现与检验。[8]
## （四）六个方面怎样串起来
文献为研究问题和路线提供证据。数据限定研究对象与泛化范围，模型表示对象，算法操作或求解模型，指标将目标转成可测量判据，实验设计组织对照并控制其他解释。五项技术安排共同检验研究问题，选择时相互核对，按结果迭代。[9]
| **方面** | **关注的问题** | **可形成的内容** |
|---|---|---|
| 文献调研 | 前人怎样定义问题？有哪些路线、强基线、反例和未解决问题？哪些证据支持本计划？ | 带来源定位的证据表，以及路线选择依据 |
| 数据 | 研究对象怎样被观测或表示？数据从哪里来？如何采集、清洗、标注、划分？有哪些偏差和使用限制？ | 数据说明、版本与划分规则 |
| 模型 | 用什么结构或假设表示对象？输入输出、参数和状态是什么？哪些固定、哪些可变？ | 模型定义、版本和基线 |
| 算法 | 怎样训练、推理、搜索或求解？核心步骤、目标函数和关键改动是什么？代价与失败条件是什么？ | 公式或伪代码、算法基线与配置 |
| 指标 | 什么叫更好？怎样测量？单位、方向、统计口径和判定条件是什么？ | 主指标、必要约束与测量协议 |
| 实验设计 | 哪个比较检验哪个假设？改变什么、控制什么？如何排除其他解释？ | 对照与消融矩阵、预算和结果判读规则 |

模型描述“研究对象怎样被表示”，算法描述“怎样操作或求解”。同一个模型可使用不同算法，同一个算法可用于不同模型。比较时说明数据、模型和算法有哪些变化，便于判断结果来自哪里。

# 三、六个方面怎样具体规划
## （一）文献调研
按“问题 → 关键词与同义词 → 检索与引文追踪 → 筛选 → 阅读 → 比较 → 研究缺口”执行，记录范围、信息截止日、检索日期、纳入和排除依据。检索、归档和阅读深度沿用[文献调研规范](<../文献调研/文献调研规范 Literature Review Standard.md>)。
文献调研时关注数据、模型、算法、指标和实验设计。核心文献可围绕以下内容做笔记：
| **字段** | **填写内容** |
|---|---|
| 问题与来源 | 研究问题、论文或官方实现、版本，以及关键章节或图表位置 |
| 数据与模型 | 数据集、划分、预处理、模型结构和规模 |
| 算法 | 方法机制、训练或推理步骤，以及最接近的基线 |
| 指标与实验 | 指标定义、对照、消融、硬件、预算和比较条件 |
| 证据与用途 | 作者结果、实际阅读范围、局限，以及对本计划的具体作用 |

引用量和发表场所用于发现线索，采纳依据是问题相关性和证据质量。论文报告的数字、自己的复现数字与跨论文摘录分别标明。条件不同的结果可用于了解路线，不能直接作为公平排名。关键证据缺失时标记待核验，未查到工作不能直接证明研究空白。[1][2]
## （二）数据
记录来源、许可或授权、版本、样本单位、规模、分布、标注来源与误差，以及收集、清洗、预处理和排除规则。涉及人或敏感信息时补充适用的伦理、隐私与使用要求。
根据泛化问题选择按实体、时间、地点或其他单位隔离的划分。数据清洗、特征处理和参数估计应按划分边界执行，避免测试信息进入训练、模型选择或校准。记录重复样本、预训练污染和分布偏差的已知情况及无法确认部分。
既有 Benchmark 优先沿用其明确协议。修改协议时说明原因和可比性。数据不能进入 Git 仓库时，保存获取说明、版本标识、划分清单或可核验摘要。
## （三）模型
说明任务输入输出、结构、参数规模、初始化或权重来源、版本、假设和适用边界。区分模型本体、训练目标、推理过程及外围系统。
选择能回答研究问题的基线，包括有用的简单基线和最接近的现有方法。改变模型规模、预训练数据或权重来源时，将其列为实验因素。纯理论或其他科学领域研究则写清变量、关系、假设和可识别条件。
## （四）算法
用公式或伪代码描述关键步骤，指出相对基线改变了哪一步、预计通过什么机制起作用。记录优化目标、超参数、停止条件、随机性、状态更新及时间或空间代价。
复用现有实现，固定仓库 commit 和配置。训练损失与最终评价指标分别说明。研究“同预算表现”时统一预算，研究“达到同质量的成本”时统一质量目标，两种比较可以并列，但须分别定义。
优先使用原作者官方代码，记录来源仓库、版本或 commit、许可证及必要适配。可沿用官方仓库，也可放入项目 `src/` 或 `reference/`，不强制固定迁入方式或逐文件计算哈希。官方实现、第三方实现与自行重写应如实区分，自行重写不能称为官方代码复现。
## （五）指标
围绕研究主张选择主指标，补充必要的质量、资源或风险约束。说明指标含义、优劣方向及影响比较的计算口径，精确测量时再细化实现版本和条件。阈值注明依据，尚未确定的值保持待确认。
关键数字保留出处，论文结果可定位到原文图表，实测结果关联日志或结果文件，汇总结果说明计算口径。区分计划目标、作者报告值与本地实测，未执行的结果保留“待测量”。
性能测量说明计时范围、预热、同步、批量与并发条件。随机实验说明重复方案和波动估计，重复次数按预期效应、方差和预算确定，不统一规定所有课题跑相同次数。
统计分析以实际独立单位为基础，区分样本差异和训练随机性。需要置信区间、显著性检验或样本量估计时，预先说明方法与假设，并同时判断实际意义。不能把相关样本当作独立重复，不能仅凭一次最好结果作稳定性结论。
## （六）实验设计
每个实验都应对应一个问题或假设，注明处理因素、对照、控制条件、评价数据、指标、重复方案、成本与判读规则。按问题选择以下类型，不强制做满组合：
| **类型** | **检验目的** |
|---|---|
| 基线复现 | 优先用作者官方代码，在关键条件相近时大致复现主要结果，了解基线表现和差距，为自己的方法建立可信对照 |
| 主对照 | 在明确的可比条件下检验整体方法效果 |
| 消融或机制分析 | 在可比条件下检验关键组成与替代解释，说明覆盖范围、作用位置和协议差异，优先从简单设置开始 |
| 稳健性与边界 | 检验数据分布、模型、参数或环境变化下的适用范围 |
| 失败分析 | 解释退化、异常、无效结果及其触发条件 |

方法创新通常先了解并复现原方法，再开展自己的改进。复现以确认主要表现、趋势和实现基本可信为目标，不要求所有数字完全一致或把原论文全部实验重跑一遍。差距较大、足以影响判断时优先排查，不能直接把未复现条件下的负结果解释为方法无效。一般可复现性因素参见 [9]。
### 1. 基线与官方复现步骤
按课题需要使用以下步骤，明确想确认的主要结果和大致可接受的差距。只有精确数值对齐关系到结论时，再细化容差和重复方案。
| **步骤** | **做法与记录** |
|---|---|
| 查找实现 | 优先查看论文、项目页和作者仓库。找不到官方代码时说明查过哪些来源，可使用可信第三方实现或自行实现，并如实标明来源 |
| 准备与对齐 | 记录代码版本及适配，尽量沿用官方配置，重点核对数据、模型、评测脚本、覆盖范围和作用位置，说明影响比较的差异 |
| 小规模检查与复现 | 先检查流程能运行，再选择代表性结果验证。可以从作者权重与评测脚本开始，按研究需要再运行训练或方法生成流程，记录实际做到哪一步 |
| 比较与后续安排 | 对照作者结果，记录主要数字、趋势、出处文件和差距。表现大致一致、关键差异可解释时即可开展自己的方法；差距影响判断时先排查，资源不足时说明限制及后续安排 |

“代码能跑”“权重复现”“训练/方法复现”分别描述实际完成的工作。使用作者权重和评测脚本验证结果，不能写成已复现训练过程；研究不涉及训练流程时，也不必因此重训整个模型。

### 2. 消融覆盖与数字追溯
消融围绕关键组成展开，比较时尽量保持覆盖范围、作用位置和评价协议一致，存在差异则说明。例如量化中 `V/O-only 56 层` 与全 `196 层` 主表属于不同条件，不能直接把数字差异归因于算法优劣。
训练、仿射、scaling、旋转等组成按研究问题选择消融，不要求穷举所有组合。建议从简单、尽量不改原始权重的设置开始，例如先无 scaling，再逐步增加关键组成。保留无效及退化结果，区分计划目标与实测值，并关联出处文件。

建立基本可信的基线后开展自研对照。模型选择和调参使用开发数据，最终测试集用于既定评价。保留探索性分析及事后修改记录，避免把看过结果后选定的指标当作预先设定。多次比较影响结论时，说明其处理方法。观察性研究须说明混杂与识别假设，相关性结果不能直接写成因果结论。
### 3. 实验选择与优化方法
先区分“检验假设、解释机制”和“寻找更好配置”，再按任务选用方法。以下方法按需采用，不要求每个课题都使用。
| **方法** | **适用问题与计划内容** |
|---|---|
| 统计实验设计（Design of Experiments，DOE） | 多因素比较时，按需使用随机化、分组和全因子或部分因子设计，考察主效应与交互作用，注明因素、水平及混杂限制 |
| 运筹学（Operations Research，OR） | 将实验选择、资源分配或调度写成决策问题，明确决策变量、目标、预算、约束和停止条件。仿真研究可结合仿真优化、候选排序与选择、重复评估预算分配。[10] |
| 贝叶斯优化（Bayesian Optimization，BO） | 适合昂贵、难以求导的黑箱目标，例如超参数或仿真配置搜索。记录搜索空间、初始试验、代理模型、采集函数、噪声处理、评估成本和停止规则，依据已观测结果选择下一次评估。[11] |
| 贝叶斯实验设计（Bayesian Experimental Design） | 以期望效用选择实验，效用可用于表达参数辨识、信息获取或决策价值。记录先验、观测模型、效用与设计约束。[12] |

OR 提供优化与决策工具，BO 用于寻找目标函数的优良取值，贝叶斯实验设计则按研究目的定义实验效用。优化配置与检验机制采用不同判据，须分别安排。采用自适应搜索时保存完整试验轨迹，说明搜索预算和公平比较口径，在独立评价数据或预定验证阶段检查选出的方案，避免将调参最优值直接当作最终证据。[9][11]

# 四、从计划到执行的简明教程
1. **记灵感**：记录触发来源、想法和初步问题，填写[研究计划模板](<研究计划模板 Research Plan Template.md>)。
2. **查文献**：提取五项技术信息，核查已有工作，形成候选路线、基线、争议和缺口。
3. **定问题与假设**：明确研究范围、预期机制和可反驳的判据，决定继续、调整或搁置。
4. **定方案与验证**：联合规划数据、模型、算法、指标及实验，写清对照、预算、结果判读，按需选用 DOE、OR 或 BO。
5. **小规模检查与基线复现**：优先沿用官方实现，先检查流程，再大致复现代表性结果，记录来源、关键条件和差距。基线基本可信后开展自己的方法，明显异常先排查。[3][9]
6. **执行与分析**：保留运行、搜索轨迹和失败记录，按预定规则分析，协议变更注明影响。
7. **形成结论与新问题**：说明支持、反驳或尚不足以判断的假设，记录边界和下一步灵感。

计划可以迭代，重要改动须记录日期、原因及影响的实验。执行前至少应能回答“为什么做、怎样比较、怎样判断、需要什么资源”。执行后应能追溯“实际做了什么、依据在哪里、结论能推广到哪里”。

# 五、不同研究类型怎样使用
| **研究类型** | **六个方面的使用方式** |
|---|---|
| 纯文献调研 | 文献是证据集合，同时比较各工作的数据、模型、算法、指标与验证条件。产出证据地图、争议和后续验证建议，实际执行范围止于调研 |
| 理论研究 | 写清对象、分布或问题实例、数学模型与假设、构造或求解过程，以定理条件、误差界或复杂度作为判据，以证明、反例和必要数值检查形成证据 |
| 方法创新 | 优先用官方实现大致复现主要结果，建立可信基线，再检验自己的改进。说明条件差异，围绕关键组成做消融，明显未复现时不直接将负结果归因于方法无效 |
| 复现研究 | 优先使用作者官方代码，重点确认主要数字和趋势，记录差距及可能原因。如实区分权重复现、训练/方法复现和第三方实现，说明实际覆盖范围 |
| 数据与 Benchmark 研究 | 重点检验采样、标注、划分、指标有效性和基线覆盖，说明评测代表什么范围 |
| 系统与应用研究 | 将任务质量与延迟、吞吐、资源和成本共同纳入评价，固定负载、硬件与端到端测量边界 |

# 六、填写示例
以下是教学设想，不代表已确定的项目或实测结果。
**灵感：** 观察到分类器预测较准确，但高置信度错误仍然出现，希望探索低成本的概率调整方法。先查文献核对现象、已有解法和评价边界，再形成以下问题。
**问题与假设：** 固定分类器后，温度缩放能否改善测试分布上的概率质量，同时满足准确率约束？预期机制是调整输出概率尺度。若主指标无稳定改善，或改善只在拟合数据上出现，假设未得到支持。
| **方面** | **示例计划** |
|---|---|
| 文献调研 | 核对概率校准定义、温度缩放及评价局限。记录各文献的校准集、模型、指标与对照，来源入口见既有[校准调研大纲](<../../../../../研发/研究/校准 Calibration/校准 Calibration 文献调研 Literature Review 大纲.md>) |
| 数据 | 固定训练、校准与测试划分，温度仅在校准集拟合。数据版本、规模及隔离单位待课题选定 |
| 模型 | 固定同一分类器与权重版本，保存原始预测，明确不更新分类器参数 |
| 算法 | 比较原始输出与温度缩放输出，固定拟合目标、搜索范围与停止规则 |
| 指标 | 以测试 NLL 为主指标，以准确率为约束，Brier 与固定分箱协议的 ECE 用于补充分析。改善门槛和统计方案在正式实验前确定 |
| 实验设计 | 在相同测试样本上配对比较，检查校准集规模变化及失败样本。若要声称跨训练随机性有效，增加独立训练重复 |

此例的具体数据、参数、预算和判定阈值须补齐后才能进入正式实验。结论仅覆盖所测模型与分布，跨任务推广需要独立验证。

# 七、放入 GitHub 仓库怎样使用
## （一）使用 research-plan skill
[research-plan skill](https://github.com/DreamSoul-AI/knowledge/tree/main/skills/research-plan) 将本规范的流程整理为可复用的 Agent 执行说明，附[中文教程与模板](https://github.com/DreamSoul-AI/knowledge/blob/main/skills/research-plan/references/README_zh.md)。
首次安装时，将下面这段消息发给 Codex：
```text
$skill-installer
请安装 https://github.com/DreamSoul-AI/knowledge/tree/main/skills/research-plan 目录里的技能。
```
安装后从下一轮对话开始调用，例如：
```text
请使用 $research-plan，将下面的灵感整理成研究计划：……
先做文献调研，再明确问题与假设，联合规划数据、模型、算法、指标和实验。
未知设置标记待确认，本次只规划，不运行训练或发布。
```
已有计划也可要求用 `$research-plan` 检查证据、六方面衔接及实验设计。规范与模板用于说明研究思路，skill 用于将其展开为 AI 执行提醒。AI 根据缺项是否影响结论决定补查、记录限制或继续，不因模板尚未填满机械停止。具体数据、预算、负责人和判断仍由课题确认。
## （二）仓库中的计划与执行
将填写后的模板保存为仓库的 `docs/research-plan.md`，在 README 链接它。既有仓库沿用原结构，下表只说明职责，不要求新建所有目录。
| **内容** | **建议位置或职责** |
|---|---|
| 灵感、文献、研究问题与假设、六方面安排 | `docs/research-plan.md`，作为当前计划入口 |
| 文献证据与引用 | 原有文档位置，规模较大时独立为 `docs/literature.md` |
| 数据与划分 | 现有数据模块及数据说明，不将私有原始数据混入 Git |
| 模型与算法 | 现有源码模块，保持已有接口和分层 |
| 实验配置与指标 | 现有配置、评测入口和必要测试，复用项目工具 |
| 运行证据与报告 | 运行日志、原始指标、制品位置及分析报告，按项目制品管理规则存放 |

每个实现任务关联一个计划中的问题或实验。Issue 描述输入、改动范围、验证方式和预期产物，PR 链接相关 Issue、实际验证与已知限制。计划中“准备实施”与仓库中“已经实现”的状态分别维护。
灵感可以先记为探索 Issue，附来源和初步问题。文献核查后再将选定问题写入计划，关联实现与实验 Issue。采用 OR 或 BO 时，在现有配置和日志中保存目标、约束、预算及试验轨迹，无需另建研究框架。
每次正式运行至少记录：实验 ID、代码 commit、实际配置与未提交差异、数据及划分版本、模型版本、依赖与硬件、随机设置、执行命令、运行状态、原始结果和制品位置。负结果与失败运行保留原因。仅记录随机种子不足以保证结果可复现。
以下指令可作为仓库 AGENTS.md 的研究任务约定，经仓库维护人按项目范围采用：
> 开始研究工作先记录灵感来源，通过文献调研明确问题与假设。实现前读取当前计划及相关代码，核对数据、模型、算法、指标和实验设计。复用已有实现，先做小规模检查及必要基线。正式运行记录版本、配置、环境、搜索轨迹和原始结果，保留失败与负结果。分别记录文献结论、假设和执行状态，报告结论边界及新问题。
