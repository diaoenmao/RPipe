# RPipe v0.3.1 发布报告

发布日期：2026-10-14（Asia/Shanghai）。上一正式版本：[v0.3.0](https://github.com/DreamSoul-AI/RPipe/releases/tag/v0.3.0)，标签提交 `804b3823ab6d2af46cbda1a65688ca8b76c60b22`。完整差异见 [v0.3.0 → v0.3.1](https://github.com/DreamSoul-AI/RPipe/compare/v0.3.0...v0.3.1)。

## 一、摘要

### （一）本版目标与成果

本版是 v0.3.0 之后的小版本，合并已有发布后实验材料、下游源码模板接入文档和 B-030 修复，并补齐研究与上游反馈约定。不是一次新训练框架或调度器改造。

1. **正确性：** report 导出前核对当前 index 与聚合中的 Study / Run 身份，拒绝旧 version 的聚合及不可用清单，原子替换数字表并保全旧证据。
2. **项目接入：** 下游复制源码并长期保留 `src/rpipe/`，项目包与 Study 按同名 structure / flow 分工；统一 Study 指南移至根 README，项目使用自己的实际入口，不以 pip 依赖作为接入方式。
3. **研究与协作：** 文档明确六方面计划、最小验证、证据边界和 knowledge skills；下游通用问题经脱敏、去重及授权反馈到 RPipe Issues，再由上游核验与收纳。
4. **实测保全：** 收入 2026-10-13 固定 v0.3.0 源码的完整探针、长实验、并发校准与中断接续证据，保留旧失败与版本快照，不改写为 v0.3.1 的实测。

### （二）验证与发布边界

本版 CPU core 为 420 passed / 2 skipped，CPU integration 为 52 passed。两项跳过是本机符号链接权限限制，不算通过。版本与文档整理没有运行新的大规模实验，已有完整科学结果仍绑定其原提交、配置和设备。

按工作分支 → PR → dev → 发布 PR → main 执行，实际提交的 Unit tests / Build package / Branch flow 全部成功后才能合并；实际 main 的 CPU / 包 CI 通过后才建立不可变标签和 GitHub Release。最终 PR、集成提交与 CI 链接补充在 GitHub Release 正文，不以旧提交检查替代。版本元数据统一为 `0.3.1`，仅发布 GitHub 源码归档，不发布 PyPI 或二进制资产。

## 二、从 v0.3.0 到 v0.3.1 的全部工作

- main_exp 的八格 600-step 前置门、32 条各自连续 80000-step 训练、32 条 own-best 独立评测、64 条完整性与固定曲线门均通过。原调度完成 30 条训练后中断，受影响两条以新身份从 step0 重跑；32 条成功训练各自连续，但整轮不是一次连续 launch。

- 报告、正式 JSON、图、资源观察、执行与接续记录及版本清单入库；原始 Run / checkpoint / 数据和 `.tmp/` 未入库。旧失败、未执行与来源限制分别保留。

详细数字只在 [main_exp 报告](../../studies/main_exp/docs/STUDY_REPORT.md)、[执行记录](../../studies/main_exp/docs/v030_execution.md)、[接续记录](../../studies/main_exp/docs/v030_recovery.md)、[main_probe 报告](../../studies/main_probe/docs/STUDY_REPORT.md)与[执行记录](../../studies/main_probe/docs/v030_execution.md)维护。本报告不重复展开科学表格，也不将 v0.3.0 之前已有的长实验算作本版新增运行。

### （二）B-030：报告来源与写入保全

[PR #33](https://github.com/DreamSoul-AI/RPipe/pull/33) 修复 fresh make 产生新 index 后，report 仍能 exit0 导出旧 process 的问题。原复现明确为 64 个旧 Run ID、0 个当前 ID，证据见 [Study 复现](../../studies/main_exp/docs/v030_stale_report_repro.json)。

- report 必须读到可用的当前 index，并核对 Study 名、全部计划 Run ID、seed 和因素归属。
- 缺失 / 损坏 / 非法清单、重复或缺少 Run、身份不一致时在导出前退出 2，提示检查计划并重新 process，不回退旧结果。
- 兼容旧 process 字段、合法部分聚合与重排行；不要求完整矩阵才能导出，不增加格式字段或索引 hash。
- 校验成功后通过已有 atomic writer 更新 NUMBERS；写入失败保留旧表，旧 process、图和研究报告不删除。
- 增补身份、损坏输入、兼容与写入失败回归，补齐既有测试清单的真实 seed / 因素。

这是报告读取合同修复，不修改 make、训练、调度或聚合算法。清单匹配不证明同一 Run 重跑后指标仍新鲜，不提供并发索引快照，也不替代研究质量判断。修复与失败回归保留在 [record.md](../development/record.md#9-b-030-报告来源校验与分支清理)，开放 bugs 中移除已修问题。

### （三）源码模板、Study 指南与项目入口

- 根 README 从包依赖式接入改为固定源码复制：长期保留 `src/rpipe/`，记录上游 commit / release 与本地差异，升级不覆盖已有改动。
- `src/<项目包名>/` 承载可复用研究实现，Study 通过同名 structure / flow 导入和薄组装；artifact 不单列为第三柱，六个阶段完整展示，目录图不强制指定阶段文件清单。
- AI 必须看选定基线的实际目录、子目录、接口和设计，不凭目录名字猜实现，不机械复制代码或填写空函数。
- 通用 Study guide 从 studies/README.md 移至根 README；Study 入口负责导航及从宏观 `docs/research/` 提取具体问题、计划和验收。
- 通用命令使用真实项目入口，不强制始终叫 rpipe；参考 smoke 明确只验收离线 CPU Toy/Stub 的源码接入与产物，不代表科学数值或 GPU 性能。
- 并发、显存预算和系数按设备 / 负载校准，不规定统一比例；当前实现默认值与可调整容量 API、未提供的 CLI 开关分别说明。
- 保留 2026-10-04 的 README 实例曲线及原日期，增加新报告入口而不替换或冒充新图；重构 prompt 保持在 README 最后。

### （四）研究规范、skills 与反馈闭环

[research.md](../development/research.md)适配 DreamSoul 研究计划规范与模板，连接文献调研、数据、模型、算法、指标和实验设计。理论 / 文献工作可以说明替代证据，不强制训练；宏观方案与具体 Study 分开，先小检查与必要基线，保留失败、负结果、协议变更、搜索轨迹和结论边界。

knowledge 的 research-plan、literature-search、paper-analysis、pytorch-project 以固定 commit `09078015ad8c80971ac4abd5b5ad2e322cd0e1a1` 引用；按任务读正文和必要 references，不复制整套教程，不把它们作为 RPipe 运行依赖，不声称已经安装或执行额外工具。来源版本与实际阅读范围留在研究规范，不声称独立核验其全部二级论文。

[feedback.md](../development/feedback.md)明确下游事实记录、归属核对、最小复现、公开脱敏、Issues / PR 去重、授权提交和回写 URL；项目专用算法留在下游。获反馈授权后 AI 可直接创建或补充 Issue，但不自动获准推送上游代码、建 PR、合并或扩大权限。公开 Issue 不包含私有资料、内部链接、凭据或安全漏洞。上游核验后分别进入 bugs、探索讨论或已批准设计，不因提出建议直接实施。

README、AGENTS、设计目录导航、Studies 入口与计划模板接通这些要求。没有自动安装 skills、监控任务、批量报单或对外 Issue 写入。

## 三、验证记录与限制

1. B-030 修复批次的定向回归 38 passed，core 420 passed / 2 skipped，CPU integration 52 passed；复制正式清单的旧聚合 CLI exit2、匹配聚合 exit0，64 个当前 ID 正确，原科学证据未写入。
2. 本次 0.3.1 元数据与文档批次重新执行 core 420 passed / 2 skipped、CPU integration 52 passed，各用独立 basetemp。首次默认 Conda / NumPy 因缺少本机 MKL runtime 在收集前失败；沿用已记录的 `MKL_THREADING_LAYER=SEQUENTIAL` 后通过。尝试历史异机 venv 路径确认本机不存在，未以该环境作为验收；原失败不算通过，也未改算法或关闭必要检查。
3. 全仓 Markdown 做 UTF-8、围栏、相对链接 / 锚点扫描，活动入口问题修复；历史字节快照的引用按原 Study 位置解释，本地 Run / 日志链接不随 clone 提供。7 份 v030 manifest 的 102 个文件大小与 SHA-256 核验通过，科学快照不因文档审校改变。
4. 本机通过 setuptools 原生 build backend 在 `.tmp/` 的源码副本构建 wheel / sdist，分别安装至新环境，版本均为0.3.1，各9条公开CLI、4个Toy/Stub Run及2个Experiment通过。安装环境复用本机科学依赖，不声称干净依赖安装；sdist首次因pip默认缓存目录写入权限失败，改用`.tmp`临时目录及禁用缓存后通过，失败保留。最终远端矩阵及main集成必须在对应提交通过，不使用本机或旧提交通过结果替代。

本次未重跑科学矩阵或 GPU / HF / 多 worker 验收，没有修改研究配方与数值门。0.3.0 发布后的完整实验属于原源码；0.3.1 的版本号改变库源码 hash，旧 freeze 不能直接作为本版来源。

## 四、升级与迁移

1. 下游按[源码接入指南](../../README.md#在其他项目中使用-rpipe)取得 v0.3.1，记录标签解析出的完整 commit，比较本地副本差异后迁移；保留 `src/rpipe/` 及许可证，不改为外部 pip 依赖。
2. 原 index / process 格式没有迁移；report 拒绝旧聚合时保留证据，使用当前 index 重新 process，再 report。不要删除旧表或关闭校验获得通过。
3. 项目与 Study 沿用两柱职责，阅读实际目录和 API；宏观计划、具体 PLAN 与研究报告按现有位置维护，不新建重复框架。
4. 来源或声明变化时保存旧证据，独立实验使用新 version / Run ID，fresh make 并执行计划规定的小门与前置对照。历史成功结果不自动成为新模板验收。
5. 并行先重新校准目标环境，保留资源、数值与单 Run 所有权边界；checkpoint 的严格恢复范围不扩大，异机要重新验收。
