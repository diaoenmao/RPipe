# RPipe v0.3.0 发布报告

发布日期：2026-10-13（Asia/Shanghai）。上一正式版本：[v0.2.0](https://github.com/diaoenmao/RPipe/releases/tag/v0.2.0)，标签提交 `75ebad0c21cbb9269251408df0ed77b5e52b6f02`，于2026-10-05 北京时间发布。完整版本差异见 [v0.2.0 → v0.3.0](https://github.com/diaoenmao/RPipe/compare/v0.2.0...v0.3.0)。

## 一、摘要

### （一）本版目标

将 v0.2.0 之后的 Study / Flow 集成、目录与文档整理、研究复验及正确性修复一起发布到 main。v0.2.0 已经提供可安装的库、统一 CLI、两柱架构、Run 产物和训练 / 评测；这些不是本版首次实现。v0.3.0 的重点是让 Study 尽量复用现有库流程，并明确来源冻结、阶段职责、成功定稿与恢复合同。

### （二）主要成果

1. Study 采用 `flow/` 和 `structure/` 两柱，库加载显式阶段扩展；阶段实现放 `run.py`，`__init__.py` 仅导出。
2. recipe 注册、provenance / freeze 和通用 `rpipe compare` 进入库；成对探针通过原生六阶段链执行，不另写调度与训练入口。
3. 原生 CPU / CUDA 单进程 checkpoint 增加 RNG 和数据位置恢复；修复设备分流、容量配置、预算停止、比较精度、重复写入、目录名称与 metric 边界。
4. 研究报告保留历史长实验、新短探针、容量 / 精度测量及原始失败，各自绑定实际源码；目录导航、Agent 约定和发布门禁同步。

### （三）发布与验证边界

工作通过 PR 进入 dev，再由 [发布 PR #30](https://github.com/diaoenmao/RPipe/pull/30) 进入 main。版本元数据为 `0.3.0`；正式标签为 `v0.3.0`。CPU 发布门覆盖 Ubuntu / Windows 和 Python 3.10 / 3.13，以及 wheel / sdist 干净安装与公开 CLI。

本版仍为阶段版，不保证所有设备、HF 或多 worker 的严格恢复。2026-10-11 的完整长实验属于当时源码；最后一轮重构 / 修复只完成当前来源的小规模验收，没有重跑当前源码的完整长矩阵。升级版本号会改变库源码哈希，不能把此前实测来源改写为新发布来源。

## 二、从 v0.2.0 到 v0.3.0 的全部工作

### （一）仓库、文档与协作整理

- 首页改为描述当前 RPipe 的能力，移除与本项目无关的致谢，保留实测图的来源与历史日期。
- 设计文档迁入 `docs/code/`，开发记录迁入 `docs/development/`，持续记录统一为 `record.md`；Study 指南放 `studies/README.md`，文档与导航链接同步。
- 正式 Study、模板与测试输入分开：测试声明放 `tests/_data/studies/`，公共恢复计算输入放 `tests/_data/`；清除旧顶层脚本、重复转调入口、过时文档与无用占位。旧发布及开发证据通过历史 Git 引用保留。
- `.gitignore` 保留 Python 通用规则并明确忽略 `.tmp/`、Study 的 runs / shared / scripts 及生成清单。少量正式版本快照的清单按明确范围入库，不把实际 Run、缓存、数据或安装包带入发布。
- `AGENTS.md` 收敛为文档驱动的通用约定，加入仓库 Markdown 排版、测试隔离、实测精度、独立 version、失败证据及异机验收要求；不依赖维护者电脑上的 DreamSoul 目录。

依据：[PR #17](https://github.com/diaoenmao/RPipe/pull/17)、[PR #19](https://github.com/diaoenmao/RPipe/pull/19)、[PR #24](https://github.com/diaoenmao/RPipe/pull/24)、[PR #27](https://github.com/diaoenmao/RPipe/pull/27)，以及 [开发记录](../development/record.md)。

### （二）库级 recipe、来源冻结与 Run 对比

- `study.yaml` 声明 `recipe`，make 校验入口；每个 Run 的 prepare 在运行条件应用后、Factory 建构前调用 `register(ctx)`。recipe 不再承担独立训练和调度。
- make 写入 provenance，记录实际导入的库源码、Study 声明、recipe、两柱源码、额外固定输入及执行清单；freeze 在 launch / run-one / Study process 的边界检查变化。生成的 Run 归档和缓存不误算为源码。
- `rpipe compare` 只读比较摘要数值、tracker history 和 model / optimizer / scheduler checkpoint；缺失或不一致不能报告通过。Study 可以将外部已有观测投影成 Run，再调用该实现。
- make 的 `flow.prepare_shared: false` 明确关闭通用数据预构造，让需要专用准备的 Study 自己承担准备职责，不通过吞掉未知 source 错误实现兼容。

依据：[PR #21](https://github.com/diaoenmao/RPipe/pull/21)、[来源与扩展合同](../code/flow.md#14-study-扩展recipe来源清单run-对比)。

### （三）Flow 与 Study 两柱及阶段职责

- `flow.study_phases` 显式启用扩展；Study 的 `flow/<phase>/` 对应 prepare、execute、collect、summarize、write、process，专用 Data / Model / Algorithm 放 `structure/`。
- prepare 增加构造前 `before(ctx)` 与构造后 `run(ctx)`；支持阶段内相对导入，并隔离不同 Study 的同名模块。
- execute 保存原始计算观测；collect 计算研究指标；summarize 执行数值门；Study write 完成附加证据与验收后，库才原子定稿成功 result。write 失败不能留下本次成功状态。
- process 区分 Run 和 Study scope。Study 终验发生在通用聚合后；派生失败保留原成功 Run 和故障证据，不把未齐全的矩阵当作完成。
- 库与 Study 的普通阶段业务从 `__init__.py` 移到 `run.py`，process 按职责拆分；空扩展目录不代表库默认阶段没有实现。清除 collect 的重复实现和导出冲突。
- 停止加载旧的 Study 根目录阶段包，明确报错要求迁移；两柱源码和手动工具自动参与来源冻结。

依据：[PR #22](https://github.com/diaoenmao/RPipe/pull/22)、[PR #23](https://github.com/diaoenmao/RPipe/pull/23)、[PR #25](https://github.com/diaoenmao/RPipe/pull/25)、[PR #28](https://github.com/diaoenmao/RPipe/pull/28)，及 [Flow 合同](../code/flow.md#140-study-阶段目录)。

### （四）两个正式 Study 的整理与复验

`main_historical` 改名为 `main_exp`，`main_reproduction` 改名为 `main_probe`；对应声明、version、Run ID、指南和入口同步。历史文件删除或替换均保留可取得的 Git / 版本证据，不重建缺失的运行事实。

main_exp 的历史建构注册复用 Data / Model Registry，准备与整轮曲线门使用 Study 阶段；数据准备、前置门、速度与精度诊断为显式手动入口。main_probe 删除独立 probe.py，将成对 Algorithm、原版先 / 当前版后的观测及自身 best 评测接入六阶段；write 使用库 compare，Study process 只验收当前 index 的完整八组合。

2026-10-11 完成当时显式 FP32 基线的两个 Study 复跑和 main_exp 长矩阵终验；原默认精度失败保留。2026-10-12 目录重构后先做有限短复验，2026-10-13 再完成最终来源的小门、完整短探针及受控容量 / 精度调查。各轮不是同一个源码基线，不能合并宣称当前发布版本再次完成长训。

归档源码导出改用 Git batch 读取，保留字节校验和损坏响应拒绝；历史运行条件的导入副作用受控。正式计划、曲线目标、门限和失败证据不通过放宽阈值改成通过。详细实验条件、数字与过程只在 [main_exp 报告](../../studies/main_exp/docs/STUDY_REPORT.md)、[速度与精度报告](../../studies/main_exp/docs/speed_calibration.md)、[main_probe 报告](../../studies/main_probe/docs/STUDY_REPORT.md) 中维护。

依据：[PR #21](https://github.com/diaoenmao/RPipe/pull/21)、[PR #23](https://github.com/diaoenmao/RPipe/pull/23)、[PR #26](https://github.com/diaoenmao/RPipe/pull/26)、[PR #27](https://github.com/diaoenmao/RPipe/pull/27)、[PR #28](https://github.com/diaoenmao/RPipe/pull/28)、[PR #29](https://github.com/diaoenmao/RPipe/pull/29)。

## 四、升级与迁移

1. 拉取 main 或安装固定标签：`python -m pip install "git+https://github.com/diaoenmao/RPipe.git@v0.3.0"`。研究 Study 需要原 Git 归档提交时使用完整 clone；仅安装 wheel 不包含研究数据、归档历史或本机 Run。
2. 更新文档入口为 `docs/code/`、`docs/development/` 和 `studies/README.md`。旧 Study 名称改为 main_exp / main_probe；不要混用已删除脚本和统一 CLI。
3. 将旧根阶段包搬到 `flow/<phase>/`，实现放 `run.py`、入口仅导出；专用建构放 `structure/`，开启 `flow.study_phases`。prepare 的构造前工作移到 before；旧 write 从读取最终 result 改为读取 result_draft。
4. 库版本、源码或声明改变会使旧 freeze 失效。先保留旧证据，再设置新的实验 version，重新 make、执行计划前置门；不能重写 provenance 后把旧成功结果当新验收。
5. 原生完整恢复限于同预算 / 配置 / runtime、受支持标准 sampler、num_workers=0 和 batch metrics 的 CPU / CUDA 通路。旧 checkpoint 可继续部分加载，但不保证与连续训练等价；HF、多 worker、私有 RNG 或自定义恢复协议另行验收。历史 Study 继续拒绝中断后续训。
6. 容量预算只针对已测设备和配方，异机重新检查可用显存、依赖、raw 与小探针。严格比较显式统一 TF32 / 混合精度并核对实际值，不只设置 seed / deterministic。

详见 [结构合同](../code/structure.md)、[Flow 合同](../code/flow.md)、[Study 指南](../../studies/README.md) 与 [交接](../development/handover.md)。

## English summary

v0.3.0 builds on the already installable v0.2.0 library. It integrates Study recipes, provenance / freeze, optional phase hooks and Run comparisons into the existing structure / flow architecture; migrates both Studies to flow / structure folders and thin package exports; and fixes native recovery, CPU scheduling, capacity settings, training budgets, duplicate writers, Run names and numeric comparisons.

The report covers every integration batch after the actual v0.2.0 tag, not only the latest bug-fix PR. CPU and distribution checks cover Ubuntu / Windows and Python 3.10 / 3.13. Scientific evidence retains its original source baseline: the last refactor / fixes passed short gates, not a new full long-training matrix. Old B-023 weights remain unavailable; the supported explicit FP32 contract passes, without claiming recovery of the original literal kernel. Worker / HF / private RNG and target-machine limits remain explicit. No PyPI or binary distribution publishing is included.
