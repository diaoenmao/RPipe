# 下游反馈与上游收纳

## 一、目的与边界

下游项目使用 RPipe 源码模板时，可能发现不兼容、缺陷或可归纳的改进。将有证据的通用问题反馈到 [DreamSoul-AI/RPipe Issues](https://github.com/DreamSoul-AI/RPipe/issues)，供维护者集中判断与收纳；创建 Issue 不等于提交代码的 Pull Request，也不等于已批准改变 RPipe。

反馈形成闭环：**下游记录 → 核对归属与脱敏 → 去重并提 Issue → RPipe 核验与决策 → 实现及验证 → 下游按固定版本复验**。不因发现一个项目需求就提前抽象框架，也不要求下游等待上游方案才能继续已有安全工作。

| **发现** | **处理位置与依据** |
| --- | --- |
| 已支持合同与实际行为不符 | 向 RPipe 报告缺陷，提供最小复现；尚未定位时写“疑似”，不把下游改动或环境问题直接断言为上游 bug |
| 接口不兼容、通用能力缺口、可复用方案 | 向 RPipe 提改进建议，说明真实场景、现有扩展为何不足、兼容风险与取舍；一个场景先作为候选，不声称已证明普适 |
| 项目算法、专用数据处理、特定指标或研究结论 | 默认留在下游 src / Study；可提炼共享机制再讨论，但不要求 RPipe 收纳领域代码 |
| 环境、硬件、性能或数值差异 | 先记录可比条件与边界；没有受控证据时标为待验证，不把单次速度或不同精度的结果当通用结论 |

## 二、AI 怎样记录与提交

1. **先在下游保存事实。** 在已有缺陷记录、研究计划或相关 Study 报告记录发现，注明上游版本、下游修改、实际条件、影响和证据。临时排错放 `.tmp/`，需要长期保留的事实不能只存在临时草稿。
2. **核对责任与复现。** 对照 RPipe 文档和固定源码，区分上游已有问题、下游适配问题与未知原因。能安全低成本验证时做最小复现；不能时注明未验证，不为提交 Issue 自动运行大规模实验。
3. **检查公开范围。** RPipe 是公开仓库。正文、日志、附件和链接均须脱敏，不提交私有仓库地址、内部文档、私有数据、模型权重、凭据或可识别用户的路径；可用 Toy/Stub 或合成输入表达问题。安全漏洞或无法公开的材料不进入公开 Issue，留在受控记录并请求维护者选择安全渠道。
4. **去重。** 检索相关关键词、模块、错误及已有 open / closed Issues 和 PR，核对是否已修复。相同问题优先补充新条件与证据；旧缺陷再次出现须注明修复版本与当前反例。不要按每条失败 Run 重复报单。
5. **在反馈授权范围内提交。** 用户已授权“向 RPipe 提 Issue / 补充已有 Issue”时，AI 可直接提交符合上述条件的反馈，无需逐条再询问。仅授权本地修改、研究或重构时，不自动获得对外写入权；缺权限或不能安全脱敏时，保存草稿并报告，不擅自扩大权限。
6. **回写结果。** 将实际 Issue URL 与提交状态写回下游长期记录。结果不明确时先查询是否已创建，不能盲目重试产生重复单；提交失败或尚为草稿不能报告“已反馈”。Issue 更新与关闭也按授权处理。

一份反馈围绕一个问题，正文至少包括：

| **字段** | **应提供的证据** |
| --- | --- |
| 类型、问题与影响 | 缺陷 / 不兼容 / 改进建议；事实、推断与提议分别写，说明影响职责或使用范围 |
| 来源与版本 | RPipe commit / release、下游副本的本地差异；能公开时给相关代码定位，不依赖私有链接 |
| 实际条件 | 环境、依赖、设备、输入或配置、精度、seed、并发和预算中与问题相关的部分 |
| 期望与实际 | 对应文档或接口合同；最小步骤、真实命令、输出、退出码及脱敏证据 |
| 当前判断与方案 | 已定位原因或待核验点、现有绕行、可复用落点、兼容风险及备选取舍 |
| 验证与边界 | 已做与未做的验证、建议回归、实际证据位置；不能提供原始制品时明确限制 |

若用 GitHub CLI，先完成认证并检索去重，再将已审查的正文保存为下游 `.tmp/rpipe-issue.md`，按授权执行：

```bash
gh issue create --repo DreamSoul-AI/RPipe --title "简述问题" --body-file .tmp/rpipe-issue.md
```

也可使用已有 GitHub connector。不要假设上游已有某个 label、assignee 或 milestone，不自动设置，不自动创建 PR、推送分支或修改仓库规则。这里是执行参考，不是运行到此就自动对外提交的脚本。

## 三、RPipe 怎样收纳

维护者或获授权的 RPipe Agent 先核对 Issue 的版本、最小复现与重复关系，再确定是上游缺陷、通用改进、正常差异还是项目专用需求。未核验 Issue 不能直接标成“已复现缺陷”。

- 已确认且未修复的缺陷进入 [bugs.md](bugs.md)，按本仓库规则分配 B 编号并链接 Issue；修复验证后移除开放条目，证据留在 [record.md](record.md)。下游不自行占用 B 编号。
- 可复用的改进先在 Issue 讨论；需要整理进 [brainstorm.md](brainstorm.md) 时，遵循当前任务授权与文档约定，建议不自动成为设计或实施合同。
- 决定实施后先更新相关设计，再通过工作分支、回归与 PR 进入 dev，发布按 [cicd.md](cicd.md) 进入 main；Issue 关联真实修复提交、验证和限制。
- 修复是否满足下游场景由下游在新固定基线上复验；上游合并不替代下游环境验收。源码副本更新先比较并保留本地差异，不直接覆盖；正式实验沿用[研究工作要求](research.md)的版本与证据约定。

本文件建立反馈方式，不启动自动监控或批量报单，也不自动授予对其他项目、Issue、PR 或云端资料的写权限。读取核验日期：2026-10-14；当日 RPipe 的 GitHub Issues 已启用，后续以实际访问权限和仓库配置为准。
