# 一、适用范围与原则
## （一）适用范围
本规范适用于源代码级自动化测试，包括：

- Unit Test（单元测试）
- Integration Test（集成测试）
- End-to-End Test（端到端测试）
- 测试范围、测试目标、测试成本、结果类型和重要性
- 测试目录、命名、标签、编写、自动化执行、结果持久化和报告
- 人工编写及 AI 生成的测试代码

本规范不展开纯外部视角的可用性测试、用户验收测试和人工探索性测试。安全、兼容性、压力测试等专项测试可复用本规范的组织与标签机制，但应另行定义专项规则。

本规范的主体与编程语言无关，具体语言和框架只负责实现这些约束。第三章第（六）节给出 Python / pytest 映射示例。

## （二）规范用语
- **必须**：不可省略，不满足即不符合本规范。
- **应该**：默认遵守，偏离时必须记录原因。
- **可以**：按项目需要采用。

## （三）核心原则
### 1. 先结构化，后自动化
统一结构用于支持人员及 AI 生成、选择、执行和分析测试。自动生成的测试必须遵守本规范，并提供与被测目标相关的有效信号。
### 2. 测试结构映射代码结构
测试目录必须复制被测程序的完整目录骨架，并保持相同的相对路径。`unit`、`integration`、`e2e` 是测试标签，不得默认作为额外的一级目录。每项测试必须能够定位到明确的源文件、对象、方法、调用路径或外部入口。测试失败后，人员或 AI 应能直接判断受影响的代码位置或调用路径。
### 3. 一个测试提供一个清晰信号
一个测试应只验证一个主要行为、契约或资源指标。禁止用一个断言入口批量检查大量不相关目标，否则失败信号过弱、无法定位。

可以通过参数化减少重复代码，但原始结果必须为每个参数用例保留独立的用例标识和状态。
### 4. 按重要性与成本渐进测试
不是所有代码都需要同等测试强度。测试覆盖范围和执行顺序必须考虑架构层级、依赖关系、运行频率、故障影响和风险，并以 `p1`、`p2`、`p3` 标记。

重要性首先从完整产品和系统的核心能力、用户影响、数据安全及恢复难度判断，再结合架构层内的依赖关系定位重点。底层引用多或上层调用少，都不能单独决定重要性。

测试范围、重要性与成本分别记录。先运行资源可用且成本较低的关键测试，再逐步扩大范围、数据规模及资源投入。高成本关键测试应安排明确的运行环境和触发条件，不得因成本高而降低其重要性。
### 5. 测试是可追踪的实验
测试执行必须可复现、可筛选、可中断恢复。每个用例结束后应尽快将结果写入磁盘，不得只依赖进程内存和终端输出。

中断恢复指利用已保存结果识别完成项、未完成项及重跑范围，不要求恢复进程内存或从任意代码行继续执行。有副作用的测试重跑前须完成隔离、清理或状态核对。
### 6. 质量信号优先于数量
测试数量、代码覆盖率和通过率都是辅助指标，不得单独作为质量结论。判定型测试必须具有有效断言，测量型测试必须具有有效采集、明确指标及测量条件。只重复实现代码、无依据地宣称通过或与真实行为无关的测试，均视为无效测试。

# 二、测试维度
| **维度** | **含义** | **表达方式** |
|---|---|---|
| 测试范围 | 测代码的哪一部分 | 目录、文件、对象、方法、接口、调用路径、系统入口，以及 `unit / integration / e2e` 层级 |
| 测试目标 | 验证什么 | `location / content / physical` |
| 测试成本 | 执行一次或一批需要多少资源 | C1 → C4，由即时反馈到大规模 benchmark，保留实际资源消耗 |
| 结果类型 | 产出什么信号 | `categorical / numeric`，内部按概览、指标、详细样本递增记录粒度 |
| 重要性 | 对整体产品和系统的影响 | P1 → P2 → P3，由高到低，标签使用 `p1 / p2 / p3` |

测试范围以代码结构为基础。架构层、模块、功能标签用于补充定位和筛选。五个维度分别表达，不从测试层级推定成本或结果类型。单个 GPU 算子的测试可以属于 `unit`，也可以成本较高并产出数值结果。

五个维度描述测试本身。测试计划与编排根据这些维度及资源条件决定测试集合、运行位置、触发时机、预算和阻断要求，见第四章。范围与成本可以由小到大，重要性由高到低；目标和结果类型是类别，结果内部另有由少到多的记录粒度。

## （一）测试范围
| **范围顺序** | **层级** | **代码结构与边界** | **示例** |
|---|---|---|---|
| 小 | `unit` | 方法、对象、源文件或单个稳定接口，聚焦一个可独立定位的单元 | 验证消息解析函数，或单个 GPU 算子的数值正确性 |
| 中 | `integration` | 多个单元组成的局部调用路径，可跨模块和服务依赖 | 从请求校验到持久化写入的调用链 |
| 大 | `e2e` | 从系统外部输入到最终用户可观察结果的完整流程 | 用户提交任务，经校验、处理、存储后在界面查看结果 |

范围按职责和依赖边界判断，不以文件数机械划线。同一模块内也可能存在集成路径。范围扩大不自动增加重要性，也不能代替成本测量。

### 1. Unit Test（单元测试）
单元测试以单个源文件、对象、方法或稳定接口作为最小定位单位。依赖默认应隔离，使失败尽量指向被测单元本身。
### 2. Integration Test（集成测试）
集成测试验证多个单元形成的局部调用路径或调用子图。它可以跨对象、模块、架构层或后端依赖，但不贯通完整的外部用户流程。

每条集成路径必须定义：

- 路径名称和业务/技术目的
- 起点、终点及关键参与单元
- 前置条件和输入
- 期望输出、状态变化或调用结果
- 是否使用真实数据库、网络、文件系统或第三方服务
- 选择该路径的原因及优先级

候选路径应基于入口程序、静态依赖、运行时调用轨迹和实际调用频率提取，并优先覆盖：

- 高频路径
- 包含多个高重要性单元的路径
- 数据写入、事务、权限和关键状态迁移路径
- 历史故障集中或跨层边界复杂的路径

集成测试可以验证调用顺序和路径行为，但这属于 `content`，不单独设置 `location`。
### 3. End-to-End Test（端到端测试）
端到端测试必须从系统外部入口开始，经过真实或等价的后端、数据库及必要的前端/接口层，并向外部调用方返回最终响应。Web、API、CLI、消息消费等系统可使用各自等价的外部边界。

端到端测试应：

- 以真实用户旅程或完整业务场景命名
- 优先覆盖少量关键主流程和关键失败流程
- 验证流程是否走通及最终用户可观察结果
- 在需要时验证总耗时等物理指标
- 与单元、集成测试分开管理，并在它们之后执行

端到端测试不是可用性测试。界面审美、主观体验和人工验收结论不属于本规范范围。

## （二）测试目标
| **类别** | **要验证的问题** | **检查依据或指标** | **示例** |
|---|---|---|---|
| `location` | 稳定代码位置和结构是否符合约定 | 路径、公开符号、目录映射和架构边界契约 | 公开服务类仍能从约定模块导入 |
| `content` | 行为与语义是否满足要求 | 输入输出、状态、不变量、异常、数值误差 | 重复请求不产生重复记录，算子误差在契约容差内 |
| `physical` | 被测对象消耗多少资源、性能如何 | 延迟、吞吐量、峰值内存/显存、资源用量 | 请求处理延迟中位数和峰值内存 |

目标是类别，不排列高低。`physical` 指被测对象的性能；测试成本包含准备、采样、清理等整个执行过程，两者的计量边界分别记录。

| **测试层级** | **定位对象** | **`location`** | **`content`** | **`physical`** |
|---|---|---:|---:|---:|
| `unit` | 单个文件、对象、方法或稳定接口 | 适用 | 适用 | 按需 |
| `integration` | 多个单元组成的局部调用路径/子图 | 不适用 | 适用 | 按需 |
| `e2e` | 从系统外部输入到最终外部响应的完整流程 | 不适用 | 适用 | 按需 |

每项测试必须且只能选择一个测试层级，每项测试必须且只能选择一个主要测试目标。沿用 `type` 字段及既有类型标签表达测试目标。
### 1. Location Test
`location` 用于稳定代码与测试的拓扑关系，可验证：

- 源模块、文件、对象或公开方法位于约定路径
- 测试文件与源文件的镜像关系正确
- 约定的模块导入路径或公开符号仍然存在
- 架构层归属与目录约束一致

规则：

- 每个用例只检查一个明确目标，不得只保留一个“全项目目录都正确”的总断言。
- 可以由脚本批量生成或参数化执行，但结果中必须逐目标展开。
- 仅对稳定的架构边界或公开位置建立位置契约，临时内部实现不应被无意义地锁死。
- `location` 只属于 `unit`，不得用于 `integration` 或 `e2e`。
### 2. Content Test
`content` 用于验证代码语义和行为，包括但不限于：

- 正常输入与预期输出
- 边界值、空值、极值和特殊字符
- 非法输入、异常类型和错误信息契约
- 输入/输出的数据类型和数据结构
- 关键中间状态、状态迁移和副作用
- 接口契约、业务规则和不变量

内容测试必须依据需求、注释、类型、接口契约和真实使用方式设计。禁止仅照抄当前实现来推导期望值。
### 3. Physical Test
`physical` 用于测量或验证被测对象的时间、空间及其他性能指标，例如延迟、吞吐量、内存/显存、CPU、磁盘或网络使用量。结果可保留数值，也可在已有阈值下给出判定。

规则：

- 没有明确预算、基线或退化目标时，不得随意编造阈值。
- 必须记录测试环境、数据规模、预热方式、重复次数和统计口径。
- 应使用稳定统计量（如中位数或 P95），避免以单次运行作为结论。
- 验证运行时间时增加 `runtime` 标签，验证内存时增加 `memory` 标签。
- 容易受共享环境影响的物理测试不得作为普通快速测试的默认阻断项。

## （三）测试成本
每项测试必须声明资源要求并记录成本信息，用于选择测试集合和安排运行频率。预计值用于调度，实际值用于复核与后续估算。成本按 C1 → C4 由小到大分级，字段 `cost_class` 使用 `c1 / c2 / c3 / c4`。

| **等级** | **具体指向** | **判定条件** | **示例** |
|---|---|---|---|
| C1 即时反馈 | 可高频重复的轻量测试 | 在项目快速预算内完成，不依赖真实 GPU、专门部署或付费调用 | 单函数边界条件、解析、权限规则检查 |
| C2 常规检查 | 普通 CPU 环境可承担的回归 | 超出 C1，仍在普通测试环境的单项及整轮预算内，无真实 GPU 需求 | 本地测试数据库集成、小型 CPU 性能回归 |
| C3 专用资源测试 | 需要 GPU 或单独资源安排的测试 | 使用真实 GPU，或超出普通环境预算，需要专用算力、较大内存、单独外部费用等，且未形成 C4 规模 | 单 GPU 图像处理或数值计算测试、固定数据规模的显存与延迟检查 |
| C4 大规模 benchmark | 大范围、多配置、重复运行的基准测试批次 | 跨实现版本、输入规模、并发数或随机种子的批量重复，或单项已达到整批基准测试的资源规模，需要独立总预算和调度 | 4 种实现 × 5 档输入规模 × 10 次重复的 200 次运行，汇总分布与性能变化 |

### 1. 分级阈值与批次成本
项目必须在测试配置中明确 C1、C2 的耗时与内存边界，以及 C3、C4 的可用资源和预算。尚无历史数据时，可使用以下建议起点，经过首次测量校准；这些数值不是跨项目固定标准。

| **边界或规模** | **初始参考** | **使用规则** |
|---|---|---|
| C1 单项预算 | 总耗时 ≤ 1 s，峰值进程内存 ≤ 256 MiB | 同时满足时间、空间和 C1 依赖条件 |
| C2 单项预算 | 总耗时 ≤ 60 s，峰值进程内存 ≤ 2 GiB | 超出 C1，但同时满足 C2 时间、空间和资源条件 |
| C3 资源预算 | 声明 GPU 数量、显存需求、预计设备占用时长或其他专用资源 | 使用真实 GPU 的测试至少为 C3，即使只执行一个方法；只模拟 GPU 接口的测试按实际资源归类 |
| C4 批次预算 | 声明配置数、每配置重复次数、单次预计成本与总设备时长、数据及费用预算 | 例如 200 次运行，每次占用 1 张 GPU 3 分钟，累计约 10 GPU·小时，不代表墙钟耗时为 10 小时 |

分级先判断 C4 批次规模，再判断 C3 专用资源，最后用项目阈值区分 C1、C2。大规模 CPU benchmark 同样可为 C4。少量重复采样以稳定中位数不自动属于 C4，也不因名称含 benchmark 就升级。

单项用例和整批执行分别定级。例如，每个任务为 C3，但参数矩阵组成的 benchmark 计划可以是 C4。计划的批次等级不能覆盖单项等级。每个等级均保留实际数值、输入规模和分级依据，等级本身不替代预算。
### 2. 成本测量项

| **成本项** | **记录要求** |
|---|---|
| 时间 | 单用例总耗时及超时预算，注明是否包含准备、预热、重复测量和清理 |
| 计算资源 | 所需 CPU/GPU 类型、数量，按需记录 CPU 时间、GPU 占用时长等，并注明计量方法 |
| 空间 | 按需记录峰值内存、显存、磁盘需求及单位 |
| 外部资源 | 网络、数据库、外部 API 等依赖及适用的计费数量、币种、费用依据 |

- 首次运行可按数据规模、历史同类测试估算，必须注明估算依据；未知值标为未知，不填零或编造数值
- 每项已执行测试至少记录总耗时；GPU、内存密集或付费测试补充对应资源的预计与可获得的实际成本，无法采集时记录原因
- 测试整体耗时属于执行成本，被测函数的延迟属于性能结果。即使计量单位相同，也必须说明测量边界
- 共享环境准备成本在运行级单列，或说明分摊方式，避免重复计入每个用例
- 并行测试的累计资源用时与整轮墙钟耗时分别报告；峰值内存不得简单求和当作整轮峰值
- 成本预算由项目环境及测试计划确定，不设置跨项目统一的任意阈值

执行预算控制“允许这项测试消耗多少资源”，性能阈值判定“被测对象是否满足要求”。例如，被测函数延迟阈值可为 150 ms，而包含环境准备和多次采样的用例超时预算可为 30 s，两者不能共用一个含义不明的字段。这里的数值仅用于说明区别。

## （四）结果类型
### 1. 信号类型
| **类型** | **标识** | **要求** | **示例** |
|---|---|---|---|
| 分类 | `categorical` | 输出明确类别，主要采用 pass/fail 二元分类，也可按契约使用多类别；可附数值及分类规则 | 耗时 120 ms，阈值 150 ms，分类为 pass；或服务状态分类为 healthy/degraded/unavailable |
| 数值测量 | `numeric` | 保留测量值、单位、统计口径和条件，不作质量判定 | 记录请求延迟中位数 120 ms 和峰值内存 256 MiB，未设达标阈值 |

### 2. 记录粒度
结果类型本身不分高低；其内部记录粒度按概览 → 指标 → 详细样本由少到多。字段 `result_detail` 使用 `summary / metrics / samples`，不增加第六个测试维度。

| **记录粒度** | **保存与呈现内容** | **示例** | **适用条件** |
|---|---|---|---|
| 概览 `summary` | 执行状态、分类结果及必要失败证据 | 重复请求测试通过，失败时列期望和实际记录数 | 不产生需保留数值指标的普通 `categorical` 测试 |
| 指标 `metrics` | 概览信息及指标值、单位、统计口径、上下文和适用阈值 | 延迟中位数 120 ms、P95 180 ms，或误差 0.001、容差 0.01 | 所有 `numeric` 用例及基于测量数值判定的 `categorical` 用例至少采用本粒度 |
| 详细样本 `samples` | 指标及逐次样本、配置/种子、分组分布和可比历史结果，原始数据可存附件 | 保存 100 次延迟、按输入长度分组的 P50/P95，以及相同配置下上一版本结果 | 排查波动、复现实验、C4 benchmark，或需要解释退化的测试 |

记录粒度控制信息量，不改变 `categorical / numeric` 语义。提高粒度不意味着必须增加重复次数，样本设计由测量目标决定。采用指标粒度时仍应保留支撑统计值的原始证据或其附件引用，报告正文可以只展示汇总。上述数值均为格式示例。

测试层级与结果类型独立，三个层级均可产出分类或数值结果。数值测量可以服务于 `content` 或 `physical`，例如数值误差或性能指标。

- 数值结果必须注明指标名称、单位、数据规模、环境、预热与重复次数，以及中位数、P95 等适用统计口径；原始样本或其附件应保留
- 只有具备明确比较规则及其所需的阈值或基线、适用容差时，才由测量结果产生质量判定，不为获得 pass/fail 编造阈值
- 同一测试可返回“延迟中位数 120 ms，要求不超过 150 ms，判定通过”；以上数值仅为格式示例
- 执行状态与质量判定分开：成功采集数值不代表性能符合要求；纯数值测量无质量判定时 `verdict` 为 `null`，执行状态为 `measured`

分类结果使用 `category` 保存，类别集合与分类规则由测试契约定义。默认 pass/fail 二元分类直接对应质量判定 `verdict`。多类别结果如 `healthy / degraded / unavailable` 可按已确认规则映射到 pass/fail；尚无质量映射时保留类别，`verdict: null`，成功完成的执行状态为 `completed`，不能自行认定质量通过。数值测量无质量判定时使用 `measured`。分类类别与执行错误、超时等框架状态分别记录。
- 测量无效、执行错误、超时和未执行不得伪装成有效数值或质量通过

## （五）重要性
### 1. 从整体影响定级
重要性为 P1 → P2 → P3，高到低，标签保持 `p1 / p2 / p3`。先判断测试对应能力在整体产品和系统中的地位，再分析局部依赖关系。代码量、引用次数、运行成本和所在架构层不能单独决定等级。

| **等级** | **宏观判断** | **失败影响与处理** | **示例** |
|---|---|---|---|
| P1 核心 | 核心用户流程、关键系统能力、数据完整性或安全边界 | 主流程不可用、数据错误或不可逆损失、权限越界；对应检查默认阻断 | 核心任务无法完成、重复写入导致数据损坏、跨用户读取数据、关键 GPU 计算错误 |
| P2 重要 | 影响正常体验或重要辅助能力，但核心目标仍可完成 | 部分场景受限、明显退化，但有可接受替代或恢复手段；纳入常规回归 | 非核心导出失败、可恢复的重试逻辑缺陷、非关键查询性能退化 |
| P3 辅助 | 对核心能力和主要用户路径影响有限 | 局部、低风险且容易恢复的问题；在相关变更或完整检查时覆盖 | 辅助诊断展示、非关键提示格式、小范围便利功能 |

同一功能的等级随产品定位变化，例如导出若是核心交付能力，应为 P1，不能因示例写为 P2 而固定套用。低频的数据损坏或安全问题仍可为 P1。高成本 C4 基准若用于核心技术方案选型或发布决策，也可能具有 P1 重要性。
### 2. 辅助评分与证据
以下五项各取 0～2 分，用于补充证据和同等级内排序，不机械地用总分覆盖宏观定级。

| **因素** | **0 分** | **1 分** | **2 分** |
|---|---|---|---|
| 核心目标关联 | 辅助能力 | 支撑重要场景 | 直接决定核心目标能否完成 |
| 影响范围 | 独立局部 | 一个模块或部分用户 | 多模块、主要用户或整体系统 |
| 数据与安全后果 | 无持久影响 | 可恢复错误或有限损失 | 数据损坏、越权或不可逆后果 |
| 恢复与替代难度 | 可立即重试或替代 | 需人工处理或存在降级 | 无可接受替代，恢复困难 |
| 暴露与故障证据 | 稳定且低暴露 | 常规使用或近期改动 | 高频、广泛暴露或历史反复故障 |

0～3、4～7、8～10 分可分别作为 P3、P2、P1 的初步参考。最终等级必须符合上一表的整体影响判断，核心能力和严重后果优先。缺少证据时暂标 P2 并记录低置信度，不填零假装低风险。

AI 或人员给出等级时应记录受影响的整体能力、失败后果、证据和判断理由。结构依赖在同一架构层内比较，作为影响传播的证据，避免天然被引用较多的底层代码挤占上层关键流程。功能定位、依赖或故障证据变化时重新评估。

# 三、组织与编写规范
## （一）目录与映射
### 1. 总体规则
测试根目录中必须建立一个与被测程序目录同名的镜像目录，并复制被测程序的有效目录骨架。这里的“复制”是复制目录层级和相对路径，不是复制生产源代码内容。

测试分类不得破坏该镜像关系：

- 不在镜像目录上方增加 `unit/`、`integration/`、`e2e/` 分类目录。
- 测试层级由强制标签区分，文件名只作为辅助识别信息。
- 测试文件必须放在其目标代码、调用路径入口或系统入口对应的镜像位置。
- 测试公共数据和辅助代码可以放在镜像目录之外的 `_data/`、`_helpers/` 中，避免与程序目录混淆。
### 2. 目录示例
假设被测程序目录如下：
```text
program/
├── main.py
├── application/
│   └── user/
│       └── service.py
└── infrastructure/
    └── database/
        └── user_repository.py
```
测试目录应复制 `program/` 的目录骨架：
```text
tests/
├── program/                                      # 与被测程序同名
│   ├── test_user_registration.py                 # 对应 main.py / 外部入口
│   ├── application/
│   │   └── user/
│   │       ├── test_service.py                   # 对应 service.py 的单元测试
│   │       └── test_create_user_flow.py          # 以该调用路径入口落位
│   └── infrastructure/
│       └── database/
│           └── test_user_repository.py           # 对应 user_repository.py
├── _data/                                    # 可选：共享测试数据
├── _helpers/                                     # 可选：测试辅助代码
└── README.md                                     # 标签、执行方式和例外说明
```
测试目录中 `program/application/user/` 与被测程序中的 `program/application/user/` 表达同一个代码位置。人员或 AI 不需要先经过测试分类目录，即可根据相对路径完成定位。
### 3. 各层级测试的落位规则
#### 3.1 Unit Test

- 放在被测源文件所在目录的镜像位置。
- 一个源文件原则上对应一个单元测试文件。文件过大时可以按对象拆分，但文件名必须保留源文件或对象信息。
- 示例：`program/application/user/service.py` 对应 `tests/program/application/user/test_service.py`。
#### 3.2 Integration Test

- 放在调用路径起点对应的镜像位置，不建立独立的 `integration/` 目录。
- 如果调用路径存在多个同级入口，应放在这些入口的最近公共上级目录对应位置。
- 文件名只需描述调用路径或场景，不添加 `integration` 类型后缀。测试层级由文件位置和 `integration` 标签共同表达。
- 路径语义不够直观时，可以在测试函数中增加一行注释或简短文档字符串。
- 测试说明中必须列出参与路径的关键单元，使其能够跨目录回溯。
#### 3.3 End-to-End Test

- 放在系统外部入口对应的镜像位置，不建立独立的 `e2e/` 目录。
- 当完整流程无法归属于单一入口文件时，放在被测程序镜像根目录。
- 文件名只需描述用户旅程，不添加 `e2e` 类型后缀。测试层级由文件位置和 `e2e` 标签共同表达。
- 用户旅程不够直观时，可以在测试函数中增加一行注释或简短文档字符串。
### 4. 镜像范围与例外

- 被测程序的有效业务目录必须在测试镜像中保留相同层级。尚无测试的目录也应保留目录占位或在清单中登记。
- 构建产物、缓存、虚拟环境、第三方依赖、生成代码和测试结果目录不需要复制，但排除项必须在 `tests/README.md` 中登记。
- 多个独立程序或服务必须分别建立同名镜像目录，不得混合为一个平铺测试目录。
- 测试文件不得放入生产源代码目录。
- 公共辅助函数不得以 `test_` 命名，避免被误收集为测试。

## （二）命名
### 1. 文件和用例
名称统一使用英文小写 `snake_case`。推荐格式：
```text
测试文件：test_<target_or_scenario>.<ext>
测试用例：test_<target>_<condition>_<expected_result>
```
示例：
```text
test_create_user_valid_input_returns_persisted_user
test_create_user_duplicate_email_raises_conflict_error
test_user_service_location_uses_application_layer_path
test_registration_flow_database_unavailable_returns_retryable_error
```
命名必须描述被测对象、条件和可观察结果，禁止使用 `test_1`、`test_normal`、`test_function`、`test_misc` 等弱语义名称。
### 2. 稳定用例标识
每项测试必须具有框架可输出的稳定标识，至少由“相对文件路径 + 用例名 + 参数用例 ID”组成。重命名导致标识变化时，应在变更说明中记录，以便历史结果关联。
### 3. 集成与端到端场景说明
集成和端到端测试必须在用例名或简短文档字符串中写明：场景目的、起点、终点和预期结果。文档字符串不得复述实现步骤。

## （三）标签与元数据
### 1. 强制标签
每项测试必须同时具有以下三个维度的标签：

| **维度** | **允许值** | **数量要求** |
|---|---|---:|
| Test Level | `unit`、`integration`、`e2e` | 恰好 1 个 |
| Test Objective（沿用 Type） | `location`、`content`、`physical` | 恰好 1 个 |
| Priority | `p1`、`p2`、`p3` | 恰好 1 个 |

组合约束：

- `location` 必须与 `unit` 同时使用。
- `integration` 和 `e2e` 不得使用 `location`。
- `physical` 应再标记具体资源类型，例如 `runtime` 或 `memory`。
### 2. 可选与额外标签
除强制标签外，可按项目需要添加以下标签。一项测试可以同时具有多个额外标签，用于组合筛选、自动化调度和报告分组。无需为每项测试填满所有类别；涉及不稳定测试、隔离测试等已有明确要求的情形，仍须按对应规则标记。

| **维度** | **推荐格式** | **示例** |
|---|---|---|
| Architecture Layer | `<name>_layer` | `system_layer`、`model_layer`、`algorithm_layer`、`world_layer`、`application_layer` |
| Module | `module_<name>` | `module_auth` |
| Feature | `feature_<name>` | `feature_login` |
| Resource | 固定短标签 | `runtime`、`memory`、`gpu`、`database`、`network` |
| Execution Trait | 固定短标签 | `slow`、`external`、`flaky`、`quarantined` |

项目可以补充业务场景或技术方向等语义标签，其具体分类由项目定义，不在通用规范中写死。例如，`unit, content, p1, application_layer, feature_login` 同时表达测试层级、目标、重要性和项目语义。

成本和结果类型通过用例元数据或统一清单表达，并能关联稳定 `test_id`。测试计划引用这些元数据选择用例，不作为用例的第六个维度。不必为每个数值创建标签。既有层级、目标、优先级标签继续使用，运行环境可用 `gpu` 等标签辅助筛选。
### 3. 标签规则

- 标签必须使用英文小写 `snake_case`，不得使用空格、中文和含义不清的缩写。
- 一个标签只表达一个维度，不得把多个含义拼接成一个标签。
- 通用标签保持稳定，模块和功能标签分别使用 `module_`、`feature_` 前缀。其他项目语义标签应登记命名约定，避免与通用标签重名或同名异义。
- 项目必须在 `tests/README.md` 或等价配置中登记所有自定义标签及含义。
- 标签必须能被执行脚本和原始结果直接解析。
- `slow`、`external`、`database`、`network` 默认不等于失败或低优先级，只表示执行特征。

### 4. 测试成本声明
每个用例必须能解析出自己的预计成本和资源要求。可在测试上声明，也可由所属模块的默认配置继承，参数用例允许覆盖。最终运行清单必须展开到具体 `test_id`，并保留默认值来源。预计成本与实际测量分开保存，实际值不得覆盖原估算。

常规轻量测试可继承资源配置，并由历史运行自动提供耗时估计，不要求人员逐用例填写全部资源字段。仅在测试使用相应资源、消耗明显或需要预算控制时，补充内存、显存、磁盘、网络和费用数据。项目应确定一个元数据主来源，存在重复声明且值不一致时必须报出冲突，不能静默覆盖。

| **信息** | **推荐字段** | **编写要求** |
|---|---|---|
| 成本等级 | `cost_class` | `c1 / c2 / c3 / c4`，记录分级依据；未知时为 `null`，受限测量后确认 |
| 总耗时估计 | `estimated_wall_time_ms` | 明确单位与测量边界，包含该用例独占的准备、执行和清理 |
| 计算用量 | `estimated_cpu_time_ms`、`estimated_gpu_device_time_ms` | 按需声明 CPU 时间或 GPU 设备占用时长，后者注明设备数量和统计方式 |
| 内存与显存 | `estimated_peak_memory_bytes`、`estimated_peak_gpu_memory_bytes` | 按需声明预计峰值，注明进程、进程树或设备等测量范围 |
| 磁盘及网络 | `estimated_disk_bytes`、`estimated_network_bytes` | 对大量临时文件、数据下载或传输的测试声明 |
| 外部费用 | `estimated_fee` | 金额、币种、计费数量及计费依据，不将不同币种直接相加 |
| 资源要求 | `resources` | CPU/GPU 类型、数量、所需内存/显存和外部服务等，作为环境匹配条件 |
| 运行预算 | `budget` | 超时、内存/显存或费用上限，由测试计划提供，可按项目规则收紧；扩大预算需符合已配置的授权范围 |
| 估算依据 | `estimate_source` | 关联历史运行、同类测试或明确的估算说明 |

成本等级或数值未知时使用 `null` 并说明原因。不适用项可以省略，只有已确认无需该资源时才填零。声明值不得误用作实际结果。未声明成本或资源条件尚不明确的测试，不得默认按低成本纳入快速配置。

未知成本可以通过受限预算下的首次测量建立估计，不必因此永久排除用例。运行前必须确认资源依赖和超时等保护条件。`gpu` 等筛选标签应与资源声明一致，遗漏标签不能绕过环境与预算检查。

以下为 GPU 数值测试的元数据结构示例，未知值需要在首次专用环境运行后补充。环境资源下限和预算应在项目的实际配置中给出。
该片段展示新增元数据，完整用例清单还须包含已有的 `level`、`type`、`priority` 和 `target` 等字段。

```json
{
  "test_id": "tests/program/compute/test_operation.py::test_operation_latency_measurement",
  "result_type": "numeric",
  "result_detail": "samples",
  "cost_class": "c3",
  "resources": {"gpu_count": 1, "gpu_model": null},
  "cost_estimate": {
    "estimated_wall_time_ms": null,
    "estimated_peak_memory_bytes": null,
    "estimated_peak_gpu_memory_bytes": null,
    "estimate_source": "首次测量，暂无历史数据"
  },
  "metric_specs": [{
    "name": "latency",
    "unit": "ms",
    "statistic": "median",
    "threshold": null
  }]
}
```

测试计划从独立清单按 `cost_class: c3` 和 GPU 资源要求选择该用例，再确定触发条件、环境和预算。GPU 型号未明确时，运行清单必须记录最终匹配的设备，未经环境可比性确认不进行跨次性能比较。
### 5. 结果类型声明
每个用例声明一个 `result_type`，并声明或继承与其匹配的 `result_detail`。测试目标 `physical`、资源标签 `gpu` 和结果类型分别表达不同含义，不能互相替代。

结果类型描述用例预定产出的信号，不随执行是否成功而改变。数值用例超时后仍为 `numeric`，其状态为 `timeout`，不能因为本次没有数值而改成 `categorical`。同一主要目标产生多项指标时可以放在一个 `metrics` 列表中，互不相关的目标仍应拆分用例。

| **用例情形** | **声明** | **必须保存的结果** |
|---|---|---|
| 输入输出、异常或结构契约 | `categorical` | 判定和失败证据，可按需附数值 |
| 延迟不得超过已确认预算 | `categorical` | 延迟数值、单位、测量条件、预算来源、比较规则和判定 |
| 观察延迟或峰值内存，无质量阈值 | `numeric` | 有效数值、单位、测量条件，`verdict: null` |
| 数值误差不得超过契约容差 | `categorical` | 误差数值、容差、比较规则及判定 |
| 服务状态分类 | `categorical` | `category`、类别集合与分类依据；按已确认规则选择是否生成 pass/fail 质量判定 |

- 数值指标须提前定义名称、单位、测量范围、统计口径和样本条件，需要质量判定时再声明阈值或可比基线及来源
- `categorical` 包含二元及多类别结果，主要使用 pass/fail。判断依据可以是数值，不得丢弃必要测量值而只保留类别
- `numeric` 可以检查样本是否完整、数值是否有限和采集是否成功，这些是测量有效性检查，不代表被测性能达标
- 预期应进行二元判定但缺少阈值时，应标为待确认，不得静默降级成 `numeric` 并视为检查完成
- 参数组合改变数据规模、资源需求或结果类型时，必须为各参数用例保留独立标识和相应元数据

## （四）测试编写
### 1. 基本结构
每项测试应采用 Arrange–Act–Assert（准备–执行–断言）或 Given–When–Then 结构，三个阶段应清晰可辨。

测试必须：

- 直接、可读，并显式表达期望结果
- 独立运行，不依赖其他测试的执行顺序或残留状态
- 在相同代码、数据和环境下可复现；数值测量应在声明的统计口径与合理波动范围内可比较
- 使用最小且具有语义的测试数据
- 在失败信息中暴露“期望值、实际值、目标位置/路径”
- 清理自己创建的文件、数据库记录、进程和网络资源

测试不得：

- 将无条件通过、空断言或只验证“没有抛异常”作为质量证据；纯测量用例必须验证采集有效性并明确其无质量判定
- 在测试中重新实现一遍生产算法并以其结果作为唯一期望值
- 捕获异常后静默忽略
- 依赖本地时间、随机数、网络或执行顺序而不进行固定或隔离
- 为了让测试通过而降低、删除或模糊有效断言
- 在一个用例中混合多个不相关行为
### 2. 断言

- 优先断言用户或调用方可观察的行为，必要时再断言关键中间状态。
- 每个用例可以有多个断言，但它们必须共同证明同一个行为。
- 异常测试必须验证异常类型。错误消息属于稳定契约时再验证关键内容。
- 数值、时间和概率结果必须使用合理容差，不得直接比较不稳定浮点结果。
- 集合比较应根据语义明确是否关心顺序和重复项。
### 3. 测试替身与依赖

- 单元测试可以使用 stub、fake、spy 或 mock 隔离外部边界和高成本依赖。
- 不得 mock 被测对象本身，也不应过度 mock 私有实现细节。
- 集成测试应尽量使用真实的内部组件，被替换的外部依赖必须在场景说明和标签中标明。
- 端到端测试原则上使用接近真实的部署和依赖。确需替换不可控第三方服务时，必须说明替换范围。
- 对调用顺序的断言仅在顺序本身是契约时使用。
### 4. 测试数据

- 测试数据应显式、最小、可读、可复现。
- 共享 fixture 只承载稳定的公共准备逻辑，不得隐藏影响断言的关键条件。
- 随机测试必须记录随机种子，失败后必须可以用该种子复现。
- 禁止使用生产环境敏感数据，脱敏样本也必须符合项目的数据安全要求。
- 数据库测试应使用隔离库、事务回滚或可验证的清理机制。
### 5. 跳过、预期失败和不稳定测试

- `skip` 必须记录原因。临时跳过还必须记录责任人或跟踪项及到期条件。
- 已知缺陷可标记预期失败，但不得把意外通过视为普通通过。
- 不稳定测试必须标记 `flaky`，记录复现信息并安排修复，不得长期依赖自动重试掩盖问题。
- 隔离测试必须标记 `quarantined`，且仍应保留在执行结果中。

### 6. 成本采集与资源控制
- 用例总耗时由执行框架覆盖准备、调用和清理阶段，代码内部针对被测操作的计时单列为性能指标
- 将预热、重复次数和输入规模写入场景配置，估算成本时计入这些工作，避免用单次操作耗时冒充整个测试成本
- 重复测量须明确冷启动、热缓存和输入状态。会修改状态的操作应在每轮恢复等价条件，或明确测量的是连续运行过程，避免预热或前一轮改变后续测试含义
- 使用适合当前运行时的计时和资源采集方式，注明进程 CPU 时间、进程常驻内存、语言分配器内存或 GPU 显存等不同口径
- 异步 GPU 操作的测量必须等待相关工作完成，明确同步边界，避免只测到任务提交时间；沿用项目已有的设备计时工具
- GPU 显存应说明已分配与预留空间等口径，重置峰值统计时不得影响并行任务的采集；无法独立归属时记录共享测量限制
- 时间和资源上限由执行器控制，尤其在超时、中断、异常时执行清理，并保存已取得的结果；普通标签或元数据声明本身不提供超时和内存限制能力
- 外部 API 调用和重复测量计入实际成本，重试记录每次消耗，费用未知时保留请求次数等计费依据
- 实际成本用于后续修正估算和运行频率，不据此自动降低测试重要性或放宽质量阈值
### 7. 数值测量与判定编写
- 先写清测什么、针对什么数据规模、如何采样和如何汇总，再实现采集与断言
- 分别保留原始样本和汇总值，说明预热样本是否排除，避免失败后只剩一句断言错误
- 在阈值断言之前保存测量结果，使数值超标时仍可生成报告；清理阶段失败时也应保留已产生的测量值
- 数值结果的采集精度与样本数应足以支撑所用统计量，不能用少量样本的偶然波动作出稳定性结论。仅需一次观测的指标注明其单次口径即可
- 使用声明的统计量与阈值比较，单位必须一致。跨基线比较需保留基线来源和适用环境，不能以本轮结果临时生成基线让测试通过
- `numeric` 成功完成时记录 `measured`，质量判定为 `null`；无效、缺失、非有限样本记录测量错误，不使用零值填补
- `categorical` 因性能超标失败时记录 `failed` 和 `verdict: fail`；环境初始化失败或采集失败记录 `error`，不伪造性能判定
- 数值、单位、测量条件及原始样本通过已有结果接口提交，不在各用例里各自实现报告生成器

## （五）AI 生成测试
AI 生成或修改测试时，除遵守全部通用规则外，还必须：

1. 先识别源代码结构、架构层、入口和依赖，再决定测试范围。
2. 为候选单元和路径给出优先级、理由及置信度。
3. 明确测试对应的源文件、对象、方法或调用路径。
4. 从需求、注释、接口、类型和使用场景推导期望，不得仅从当前实现反推期望。
5. 生成强制标签和稳定、可读的测试名称，声明成本等级、预计成本、资源要求、结果类型和记录粒度，并据此选择或生成测试计划。
6. 在资源适配的环境中实际执行新增/修改测试。判定型测试应检查目标行为被破坏时是否失败，测量型测试应检查采集是否有效以及无效测量是否被识别。因资源条件未执行的项目必须在报告中列出。
7. 不得未经授权修改生产代码来迎合测试，也不得删除既有有效测试。
8. 无法判断业务语义、性能阈值或真实期望时，必须显式标记待确认，不得编造。

AI 选取集成路径时，应同时分析静态调用关系和可获得的运行时轨迹。只有静态证据时必须说明推断性质。

## （六）Python / pytest 映射示例

### 1. Marker 注册
项目应在 pytest 配置中注册所有 marker，开启未知 marker 检查。示例：
```ini

markers =

    content: 内容与行为测试
    physical: 物理资源指标测试
    p1: 最高优先级
    p2: 中等优先级
    p3: 较低优先级
    system_layer: 系统层
    model_layer: 模型层
    algorithm_layer: 算法层
    world_layer: 世界层
    application_layer: 应用层
```

以下普通用例示例显式声明结果类型，资源要求和预计成本从项目或模块配置继承。首次估计未知时按第三章第（三）节的受限测量规则处理。

### 5. 成本及数值结果示例
以下示例复用项目提供的 `operation`（被测操作）、`measurement_context`（输入规模、环境及测量边界）和 `latency_budget`（含 `value_ms`、`source` 的已确认预算）fixture。示例展示 CPU 操作耗时，不能直接用于异步 GPU 计时。样本数量是演示配置，实际项目应根据测量稳定性和预算设置。

这里的 `latency_budget` 是被测操作的性能阈值，与执行器的超时和资源预算独立。`operation` 必须能在等价条件下重复执行，或由 fixture 显式管理状态。下方示例成本等级未知，通过受限首次测量确认 C1 或 C2，超出普通环境预算则按 C3 安排。`cost` marker 的 `gpu_count` 是简写，适配时归入 `resources.gpu_count`，不是消耗数值。

共享采集函数应放入现有测试辅助代码中，两种结果类型使用同一个采集逻辑：

```python
import math
from statistics import median
from time import perf_counter


def measure_latency(operation, *, warmup=3, repeats=10):
    if (type(warmup) is not int or type(repeats) is not int
            or warmup < 0 or repeats < 1):
        raise ValueError("invalid measurement counts")
    for _ in range(warmup):
        operation()
    samples = []
    for _ in range(repeats):
        started = perf_counter()
        operation()
        samples.append((perf_counter() - started) * 1000)
    if not all(math.isfinite(value) and value >= 0 for value in samples):
        raise ValueError("invalid latency samples")
    return {
        "name": "latency",
        "value": median(samples),
        "unit": "ms",
        "statistic": "median",
        "samples": len(samples),
        "warmup_iterations": warmup,
        "raw_samples": samples,
    }
```

纯数值测量不设置质量阈值，保留数据供报告或后续基线分析：

```python
import pytest


@pytest.mark.unit
@pytest.mark.physical
@pytest.mark.runtime
@pytest.mark.p2
@pytest.mark.algorithm_layer
@pytest.mark.result_type("numeric", detail="samples")
@pytest.mark.cost(cost_class=None, estimated_wall_time_ms=None, gpu_count=0,
                  estimate_source="首次测量，等待历史数据")
def test_operation_latency_measurement(
    operation, measurement_context, record_property,
):
    metric = measure_latency(operation)
    metric["context"] = measurement_context
    metric["threshold"] = None
    record_property("metrics", [metric])
```

基于数值进行二元判定时，先保存数据，再断言已确认阈值：

```python
@pytest.mark.unit
@pytest.mark.physical
@pytest.mark.runtime
@pytest.mark.p1
@pytest.mark.algorithm_layer
@pytest.mark.result_type("categorical", detail="samples")
@pytest.mark.cost(cost_class=None, estimated_wall_time_ms=None, gpu_count=0,
                  estimate_source="首次测量，等待历史数据")
def test_operation_latency_within_budget(
    operation, measurement_context, latency_budget, record_property,
):
    limit = latency_budget["value_ms"]
    if not math.isfinite(limit) or limit < 0 or not latency_budget["source"]:
        raise ValueError("invalid or untraceable latency budget")
    metric = measure_latency(operation)
    metric["context"] = measurement_context
    metric["threshold"] = {
        "operator": "<=", "value": limit, "source": latency_budget["source"],
    }
    record_property("metrics", [metric])
    assert metric["value"] <= limit, (
        f"median latency {metric['value']} ms exceeds {limit} ms"
    )
```

上述片段共享前面的导入与辅助函数，fixture 由项目实现。`record_property` 用于向测试结果附加属性，不会自行写入本规范的 `events.jsonl`。执行适配代码须读取属性、合并 marker 或清单元数据，并采集实际总成本。

pytest 为 setup、call、teardown 分别生成报告，适配代码应按用例和尝试合并阶段结果。`record_property` 附加的属性可通过报告传递，应直接读取结构化属性，避免从 JUnit XML 字符串反向解析。接口依据见 [pytest API reference](https://docs.pytest.org/en/latest/reference/reference.html#pytest-runtest-makereport) 和 [record_property](https://docs.pytest.org/en/latest/reference/reference.html#record-property)。
### 6. 声明、执行与报告的字段对应
| **声明或数据来源** | **执行处理** | **结果与报告字段** |
|---|---|---|
| `cost` marker 或成本清单 | 解析 `cost_class`，展开预计成本、检查资源与预算，记录分级及估算依据 | 用例 `cost_class`、`cost` 中的预计字段，以及 `manifest.json` 中的资源要求 |
| 执行器计时及资源采集 | 覆盖用例准备、执行、清理，单列共享成本 | `duration_ms`、实际成本及预算偏差 |
| `result_type("numeric")` | 成功采集后检查数据有效性，不生成质量通过结论 | `result_type: numeric`、`status: measured`、`verdict: null` |
| `result_type("categorical")` | 根据契约分类，以 pass/fail 为主，多类别仅在明确质量映射时产生判定 | `result_type: categorical`、`category`、执行状态及 `verdict` |
| `result_type(..., detail=...)` | 解析结果类型与 `result_detail`，验证 numeric 至少保留指标，采样数据关联附件 | `result_type`、`result_detail` 与报告展开粒度 |
| `record_property("metrics", ...)` 或已有结果接口 | 提取单位、统计量、上下文、阈值和样本，必要时将大样本写入附件 | `metrics`、`artifacts` 和数值报告 |
| 缺少设备、预算不足或未选中 | 记录未执行原因及后续运行条件 | 运行清单与报告的未验证范围 |

适配代码必须区分初始化/清理错误、无效测量、超时和质量断言失败。对 `numeric`，只有准备、采集、清理均成功且数据有效时才能转换为 `measured`。对 `categorical`，正常完成后保存类别，pass/fail 分类或具备明确质量映射的分类生成判定；其余多类别结果使用 `completed` 和 `verdict: null`，发生初始化、采集或清理错误时，本次尝试整体不能计为通过。保留各阶段原始状态、已得到的数值和断言证据，汇总时优先呈现错误或超时，整体 `verdict` 为 `null`，已有失败证据不得被后续清理错误覆盖。

首次接入或修改执行适配、结果映射和报告逻辑后，至少验证一次二元判定失败仍保留数值、一次纯测量不会计入质量通过数，以及一次采集失败不会被转换为有效测量。GPU 或付费测试还应验证环境不匹配时会记录未执行原因，且不会误进入常规 CI。普通用例修改按影响范围验证，无需重复验证整套适配机制。

## （七）默认决策说明
以下默认值用于项目实施，具体预算与阈值由项目确定：

| **事项** | **默认决策** |
|---|---|
| 优先级数量 | 使用 `p1`、`p2`、`p3` 三级 |
| 重要性依据 | 整体产品与系统影响优先，五项 0～2 分辅助评分，不机械按总分定级 |
| 测试命名 | `test_<target>_<condition>_<expected_result>` |
| 目录模板 | 完整复制被测程序目录骨架，测试层级用标签区分，不增设分类目录 |
| 集成路径边界 | 完整外部流程之外的关键局部调用子图，不固定节点数量 |
| E2E 边界 | 外部输入进入系统并返回最终外部可观察响应 |
| 结果格式 | `manifest.json` + 逐用例 `events.jsonl` + 自动生成的 `report.md` |
| 测试成本 | C1～C4，单项与批次分别定级，预计与实际数值分开 |
| 结果类型 | `categorical / numeric`，记录粒度为 summary/metrics/samples，执行状态与质量判定分开 |
| 测试计划与编排 | 在五个维度上组合选择，分别指定位置、触发、预算、顺序、结果粒度和阻断条件 |
| Python 映射 | pytest marker + 统一执行脚本 |

这些默认值在获得项目运行数据后可以调整，但调整必须记录依据并保持结果可追踪。

# 四、自动化与报告
## （一）测试计划与编排
测试计划是应用五个维度安排实际执行的方法，不单列为测试维度。同一用例可以被多个计划选择，不需要复制测试文件。计划应保存为项目已有配置或清单，并可生成最终用例列表。
### 1. 计划组成
| **计划项** | **含义与选择** | **示例** |
|---|---|---|
| 验证目的与范围 | 当前改动或决策需要验证什么，选择对应目录、方法、路径及层级 | 修改消息解析后检查直接单元及受影响调用路径 |
| 重要性与成本 | 选择哪些 P 等级、C 等级，哪些属于必须完成项 | PR 中完成相关 P1/P2、C1/C2；关键 C3 单独安排 |
| 运行位置 | 本地机器、普通 CI runner、专用 GPU 机器或集群 | GitHub Actions 调用普通 CPU runner 或专用 GPU runner |
| 触发条件 | 手动、代码提交、PR、定时、发布或技术方案选型前 | GPU 测试在相关变更后触发，C4 在技术方案选型前触发 |
| 预算与规模 | 总耗时、并发、内存/显存、设备时长、费用、配置数和重复次数 | 200 个配置运行限用 2 张 GPU，声明总设备时长预算 |
| 顺序与依赖 | 先执行哪些检查，失败后停止哪些依赖任务，哪些可以并行 | 先确认加载与数值正确，再开始批量性能采样 |
| 结果与报告 | 选择何种记录粒度、比较基线及归档位置 | C4 保留样本、种子、环境和分组分布 |
| 完成与阻断 | 必须完成哪些检查，失败、超时、未执行分别如何处理 | 关键用例缺少结果时检查未完成，不放行合并或发布 |

本地和 GitHub CI 是运行入口及位置安排，不代表测试只有两类。GitHub CI 可以调度专用机器，GPU 也可以在本地运行；是否纳入计划取决于真实环境与预算。以下为配置示例，不表示项目已经部署了这些流水线。
### 2. 典型计划示例
| **计划** | **用例选择** | **位置与触发** | **预算、结果与完成条件** |
|---|---|---|---|
| 本地快速反馈 | 受影响范围的 C1，优先 P1/P2 | 本地，编辑后手动或工具触发 | 限制整轮快速预算，普通判定看概览，失败保留证据 |
| PR 常规检查 | 相关 C1/C2 的单元、集成及必要完整流程 | GitHub CI，PR 或提交触发 | 在普通 runner 预算内完成，必需检查失败或未执行均不能放行 |
| GPU 专项回归 | 相关 C3，优先核心 P1 路径 | 本地 GPU、专用服务器或适配 GPU runner，相关改动或定时触发 | 核对显存、设备时长、并发与资源隔离，性能结果至少保留指标 |
| 大规模 benchmark | C4 批次，内部包含不同成本的用例，按实现/输入规模/重复次数展开 | 专用机器或集群，手动、定期或决策前触发 | 预先估算批次成本，先小样本验证，再扩展矩阵，保留详细样本及可比基线 |
| 发布前综合验证 | 产品要求的关键 P1/P2 及相关 P3，跨 C1～C4 按需选择 | 多环境分派，发布前汇总 | 必需结果齐全，注明豁免和缺失；不因发布就无条件重复所有 C4 |

Fast / Core / Extended / Full 可继续作为项目已有计划名称，但不再作为通用分级。每个名称必须明确对应选择条件、环境、预算和完成规则。
### 3. 渐进执行规则
1. 根据变更或决策目标列出必需检查，再依据重要性、成本和可用资源安排顺序。
2. 先完成低成本正确性和环境检查，再启动依赖这些结果的 GPU 或大规模测试。无依赖关系的任务可在资源允许时并行。
3. C4 先验证少量配置的数据、采集和结果格式，再展开批次。少量预检完成不能替代整批测试结果。
4. 预算不足、环境缺失或上游检查失败时保留未执行清单、原因及后续安排。不能把未执行算通过，也不能通过降级 P 等级规避必需检查。
5. 复用历史结果需核对代码、输入、环境和阈值的适用性，并在报告中标明来源。仅名称相同不足以复用。

计划记录 `plan_id`，批次记录 `batch_cost_class` 及配置矩阵。用例结果分别保留自身 `cost_class`，报告同时汇总整批预计和实际消耗。计划可提升结果记录粒度，不能删掉原有质量判定或必要证据。

## （二）自动化流程
1. 收集用例及五个维度的元数据，结合代码变化与环境能力选择测试计划。
2. 生成测试清单，记录预计成本、预算、未选项及原因。
3. 按计划渐进执行，逐用例记录执行状态、判定、测量结果、实际成本、重试及证据。
4. 从已持久化结果自动生成 Markdown 报告，供人员及 AI 分析和选择下一轮测试。

复用已有执行框架和脚本。报告可从保存结果重新生成，不应依赖测试进程仍在运行。进程中断后，由外部执行器或下一次恢复运行生成部分报告，明确哪些结果尚未保存，恢复后补齐结果并保留各次尝试记录。
## （三）执行入口
项目必须提供统一、非交互式测试入口，并至少支持：

- 按测试层级执行：`unit` / `integration` / `e2e`
- 按测试类型执行：`location` / `content` / `physical`
- 按优先级执行：`p1` / `p2` / `p3`
- 按架构层、模块、功能和任意标签组合执行
- 执行指定文件、用例或调用路径
- 执行全部测试
- 按结果类型、成本等级、资源要求及预计成本筛选
- 生成机器可解析的原始结果

筛选条件必须支持组合，且执行清单必须在运行前或运行清单文件中可见。

## （四）超时、重试和退出码
- 每类测试应设置合理超时，超时必须作为独立状态记录。
- 重试必须记录每次尝试，最终结果不得只保留成功的一次。
- 因重试才通过的测试应标记为不稳定信号，不得等同首次通过。
- 测试入口必须以非零退出码表示存在阻断性失败、错误或超时。
- 测试计划要求的关键用例未执行时，应将相应检查标记为未完成，并按该计划阻断，不能因已执行子集全部通过而放行
- `xfail` 表示已知问题仍存在，`xpass` 表示预期失败的用例意外通过，报告需单列；是否阻断由计划明确，不能静默并入普通通过率

## （五）结果持久化
每次执行必须生成唯一 `run_id`。推荐目录（项目临时目录约定优先）：
```text
.tmp/test-results/<run_id>/
├── manifest.json         # 执行环境、筛选条件、代码版本、开始时间
├── events.jsonl          # 每个用例结束后立即追加一条结果
├── report.md             # 自动生成的测试报告
└── artifacts/            # 日志、截图、原始测量样本及失败证据
```
`events.jsonl` 的每条结果至少包含：
```json
{
  "run_id": "20260814T103000+0800_ab12cd",
  "attempt": 1,
  "test_id": "tests/program/application/user/test_service.py::test_create_user_duplicate_email_raises_conflict_error",
  "level": "unit",
  "type": "content",
  "priority": "p1",
  "tags": ["application_layer", "feature_user_creation"],
  "target": "program/application/user/service.py::UserService.create_user",
  "result_type": "categorical",
  "plan_id": "pr_checks",
  "cost_class": "c1",
  "result_detail": "summary",
  "environment_id": "cpu_ci",
  "verdict": "pass",
  "category": "pass",
  "metrics": [],
  "cost": {"estimated_wall_time_ms": 20, "actual_wall_time_ms": 18},
  "status": "passed",
  "duration_ms": 18,
  "started_at": "2026-08-14T10:30:01+08:00",
  "failure": null,
  "artifacts": []
}
```
规则：

- 状态至少支持 `passed`、`failed`、`measured`、`completed`、`error`、`skipped`、`xfail`、`xpass`、`timeout`；质量判定 `verdict` 使用 `pass`、`fail` 或 `null`。未执行或无有效质量判定时为 `null`。`completed` 用于分类完成但无质量映射的情形，`measured` 用于数值测量完成。
- `category` 保存分类结果，默认与 pass/fail 判定相同；多类别须保存分类规则及质量映射来源。数值用例或尚未取得有效分类时为 `null`
- 每个用例完成后必须及时写盘，进程异常结束时，已完成结果必须可恢复。
- 仅调用 `record_property` 或在内存中汇总不算写盘。普通用例在尝试结束后落盘，长时间或高成本测量可按批次保存样本，避免强制逐样本写盘干扰性能测量
- `manifest.json` 必须记录代码版本/提交、运行命令或筛选条件、操作系统、语言/运行时版本、关键依赖版本及环境标识。
- 失败信息必须保留异常类型、精简堆栈和关键实际值，敏感信息必须脱敏。
- 原始结果必须保持机器可解析
- `manifest.json` 同时记录 `plan_id`、计划内容、`batch_cost_class`、配置矩阵、预算、已选清单、未选及未执行项原因、资源配置和预计成本依据；共享准备成本在运行级单列
- 每次尝试单独记录 `attempt`，失败后重试通过仍保留首次失败，避免汇总时重复计算用例数或漏算成本
- `duration_ms` 为该次尝试的实际总耗时，与 `cost.actual_wall_time_ms` 含义一致；成本未知项使用 `null` 并记录原因
- 数值用例的 `metrics` 必须记录有效测量，不能只保留最终 pass/fail；纯测量用例使用 `status: measured`、`verdict: null`

以下为附带数值依据的二元判定用例字段片段，具体数值仅用于展示格式，应与上方身份、环境、成本字段一起保存：
```json
{
  "result_type": "categorical",
  "result_detail": "samples",
  "status": "passed",
  "verdict": "pass",
  "category": "pass",
  "metrics": [{
    "name": "latency",
    "value": 120,
    "unit": "ms",
    "statistic": "median",
    "samples": 10,
    "warmup_iterations": 3,
    "context": {"data_size": {"batch_size": 1}, "measurement_scope": "operation_only"},
    "threshold": {"operator": "<=", "value": 150, "source": "项目已确认性能预算"},
    "raw_samples_artifact": "artifacts/latency_samples.json"
  }]
}
```
纯测量用例将 `result_type` 改为 `numeric`、`status` 改为 `measured`、`category`、`verdict` 和 `threshold` 设为 `null`，`result_detail` 至少为 `metrics`。阈值来源必须能回溯至项目实际契约或记录。
## （六）自动化报告
每轮全部或部分测试结束后必须生成 Markdown 报告，至少包含：

| **报告内容** | **要求** |
|---|---|
| 执行概况 | `run_id`、`plan_id`、代码版本、环境、预算、时间和完成状态 |
| 范围与目标 | 按代码位置、层级、模块及 `location/content/physical` 汇总 |
| 重要性与判定 | 各优先级的通过、失败、错误、超时和未执行情况，明确阻断项 |
| 数值结果 | 按结果类型和记录粒度展示，保留指标、单位、阈值、样本附件和可比基线；C4 按配置与种子分组 |
| 测试成本 | 按 C1～C4 汇总，区分单项与批次等级，记录实际成本、预计偏差及测量边界 |
| 缺陷与证据 | 失败的源代码位置或调用路径、期望与实际值、重试情况及证据附件 |
| 未验证范围 | 未选、跳过、预算不足、缺失环境、中断或缺少必需阈值的项目，以及后续运行条件 |

报告应保留额外标签，并支持按架构层、模块、功能及项目自定义语义标签分组汇总。

按计划完成的纯数值测量属于测量任务已完成，同时注明“未作质量判定”，不因其没有阈值而视为执行未完成。整体运行完成度、测量有效性、质量判定及 CI 是否放行分别呈现。

报告必须区分用例数、尝试次数、测量完成数和质量通过数。通过率注明分母，跳过、未执行及纯测量结果不算质量通过。跨版本性能比较应确认环境、数据规模和统计口径可比，不能直接把环境变化判为代码退化。AI 分析须区分已观察结果、原因推断和处理建议。

## 目录

- 镜像：`tests/rpipe/` 对应 `src/rpipe/`。不设 `tests/unit/`、`tests/integration/`、`tests/e2e/`。
- 系统入口是 `src/rpipe/flow/cli.py`。端到端用例放在 `tests/rpipe/flow/`，标签为 `e2e`。

- 公共数据在 `tests/_data/`，不放进 `tests/rpipe/` 镜像。
- 不镜像：`__pycache__/`、`.pytest_cache/`、`.egg-info/`、`.tmp/`、虚拟环境、Study 生成的 `runs/`、`shared/`、`scripts/`。

## 预算起点

沿用正文的初始参考，首次测量后再改：

| 等级 | 起点 |
|---|---|
| C1 | 总耗时不超过 1 s，峰值进程内存不超过 256 MiB，无真实 GPU、无外网 |
| C2 | 超出 C1，总耗时不超过 60 s，峰值进程内存不超过 2 GiB，无真实 GPU |
| C3 | 真实 GPU，或超出 C2 的单项 |
| C4 | 跨配置、规模或种子的批量基准 |

真实 GPU 的用例同时标 `gpu`。`cost_class` 用 `@pytest.mark.cost(cost_class='c1')`。`result_type` 用 `@pytest.mark.result_type('categorical', detail='summary')` 或 `numeric`。缺这两个声明时收集失败。

当前用例都是判定型，`result_type` 为 `categorical`，`result_detail` 为 `summary`。尚无纯测量用例。

## 标签

强制：`unit` `integration` `e2e` `location` `content` `physical` `p1` `p2` `p3`。

架构层：`structure_layer` `flow_layer`。

模块：`module_api` `module_control` `module_data` `module_model` `module_algorithm` `module_system` `module_artifact` `module_make` `module_cli` `module_runner` `module_process`。

资源与执行：`runtime` `memory` `gpu` `slow` `external` `flaky` `quarantined`。

登记处：`pyproject.toml` 的 `markers` 与 `tests/README.md`。

## 执行

`python tests/run.py`。结果目录是 `.tmp/test-results/<run_id>/`（`manifest.json`、`events.jsonl`、`report.md`、`artifacts/`）。

| 入口 | 选择 |
|---|---|
| `--fast` | `unit and p1`，排除 `slow` / `external` / `gpu`，只要 `c1` |
| `--core` | `unit`，排除 `slow` / `external` / `gpu`，`c1` 与 `c2` |
| `--cost-class c3` | 按成本等级收窄 |
| `--all` | 全部收集到的用例 |

`events.jsonl` 记录 `cost_class`、`result_type`、`result_detail`、`verdict`、`attempt` 和 `cost.actual_wall_time_ms`。预计耗时未逐条测量时为 `null`。
